# Spec: anti-loop guardrail and per-run token ceiling in PFactory and TFactory

## Design

Neither repo has AIFactory's `agents/guardrails.py` or `act_loop_hooks.py`, so
each gets one new module, `apps/backend/agents/run_guard.py` (same code, env
prefix `PFACTORY_` / `TFACTORY_`):

- Tool-call guardrail (the three #474 policies: repeated identical failure,
  same-tool failure, idempotent no-progress), thresholds env-tunable. On unless
  `<P>_ACT_GUARDRAIL` is `0|false|no|off`.
- Hooks `guardrail_pretool_hook` / `guardrail_posttool_hook`, registered in
  `core/client.py` `create_client` (PreToolUse for all tools, new PostToolUse),
  bound by `register_session(project_dir, spec_dir)` (fresh controller per
  client). They never raise into the agent. The guardrail halt is per session:
  it ends that session and is not stored, so no stale-halt file exists.
- Active stop (codex finding 1): `run_agent_session` (`agents/session.py`) checks
  `guard_halt(spec_dir)` after every streamed message; on a halt it calls
  `client.interrupt()` once (best effort, in try/except) and keeps draining the
  stream until the SDK's final `ResultMessage` so the session's usage is still
  recorded exactly once, then returns `("error", reason, {"type": "guardrail_halt", ...})`. It clears any old
  halt for the spec dir before sending the query. A halted controller also blocks
  further tool calls in the pre hook. Non-Claude providers (Ollama, OpenAI
  compatible) do not go through `create_client` hooks: they keep their own
  `max_turns` and are out of scope.
- `<P>_MAX_TURNS` replaces the literal 1000 (default 1000; non-numeric ignored).
- `<P>_RUN_TOKEN_CEILING`, default 10,000,000, `0` disables. Counted where each
  repo already counts usage, and stateless so it needs no reset and survives a
  process boundary:
  - TFactory: the spec's persisted usage in `status.json`
    (`usage_block_from_status`, input + output, summed over planning, generation,
    evaluation and handback retries, in-pod or Job). `ceiling_exceeded(spec_dir)`
    returns `token_ceiling: ...` when it is over. `run_agent_session` checks it
    before sending the query (no further paid work from any caller, including
    evaluator votes and generation) and after `record_in_status`; either way it
    returns `("error", reason, {"type": "token_ceiling", ...})`. The triager
    envelope (`_status_verdict`) forces outcome `failure` with that
    `halt_reason`, and `run_verify_pipeline` returns `ok=False` when the spec is
    over the ceiling after triage, so the durable job state agrees with the event
    even if the last vote crossed the ceiling after writing valid verdicts. The run boundary is the spec, the same scope as the reported
    usage block; raising or zeroing the env var is how a task over the ceiling
    is allowed to continue (a rerun re-trips otherwise).
  - PFactory: `PlanSession.record_usage` (the plan run's own `PlanUsage`, already
    the event `usage` block). `_decompose` checks the session total before any
    paid call (so a retry of an over-budget session never calls the LLM) and
    `record_usage` checks again after. Over the ceiling either raises `TokenCeilingExceeded`;
    `process()` already turns an exception into status `failed` with
    `process_error` = the class name, and now also calls `emit_usage_snapshot`
    before re-raising for that class so the typed event reaches CFactory
    (codex finding 4). `build_completion_event` adds `halt_reason: token_ceiling`
    when `process_error == "TokenCeilingExceeded"`.

## Alternatives rejected

- Copy AIFactory's `act_loop_hooks.py` whole: it carries the mutation ledger,
  context summary and test-evidence hooks that do not exist here.
- Share one package across repos: Factory#3709 is moving that way for the sandbox,
  but a cross-repo vendored file adds byte-check CI for ~120 lines; revisit if a
  third change lands.
- Count PFactory agent-session tokens too: PFactory's SDK sessions are short and
  single-shot and record no usage today; the plan run total is the real spend.

## Risks

Default-on guardrail may halt a legitimate run that repeats a failing call; every
threshold is env-tunable and `off` restores the old behaviour. The ceiling is
checked at session boundaries (TFactory) or after decompose (PFactory), so one
session can overshoot. TFactory counts input + output only (cache tokens are not
in `RunUsage`). Two concurrent clients on one project dir share a hook key; the
last `register_session` wins. A TFactory guardrail halt ends one session and the
callers treat it as the session error they already handle; it is not stamped on
the completion event (only the token ceiling is).

## Verification

Unit tests per repo: guardrail on by default and off switch, repeated failing call
halts, ceiling halts and `0` disables, max-turns env, the
session stops on a halt and returns a typed error, and a session over the TFactory ceiling never sends its query; a halt before `ResultMessage` still records usage; a last-vote overshoot makes the pipeline return not-ok; retrying an over-budget PFactory session never calls the LLM; PFactory `process()` fails with the typed
reason on a tiny ceiling; TFactory envelope is `failure` with `halt_reason`; PFactory sends the snapshot with `halt_reason`. Repo lint and the
existing suites for touched files.
