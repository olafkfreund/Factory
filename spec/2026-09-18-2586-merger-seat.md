# Spec: finished builds reach a human as a pull request

All work is in AIFactory (`origin/dev`), extending the existing merger
(`apps/web-server/server/services/merger.py`). Paths below are relative to
`apps/web-server/` unless stated otherwise.

## Design

### 1. Look up the PR in every state first, then measure the worktree

`merger._decide` currently runs: open-PR check, then measure
`origin/<branch>` against `origin/<base>`, then open a PR. The new order is:

1. **PR lookup, all states.** Replace `_find_open_pr` with
   `_find_pr(owner, name, branch, runner) -> (measured, number, state)`, using
   `gh pr list --head <branch> --state all --json number,state`. Prefer an
   OPEN PR; otherwise take the most recent one. A failed query stays
   `open_pr_check_unmeasurable`, never "no PR".
   - `OPEN` returns `already_open`, as today.
   - `MERGED` returns the new action `merged`. **No new PR is opened.** This
     matters: task 001's squash-merged commits are still in its local branch
     under different SHAs, so once the merger measures locally (step 2),
     without this check it would reopen already-merged work.
   - `CLOSED` returns the new action `closed`. No new PR: a human rejected it.
2. **Measure the local branch, not the origin copy.** `_branch_ahead_and_changed`
   compares the worktree's local `refs/heads/<branch>` (falling back to
   `origin/<branch>` when there is no local ref, which is the packed path)
   against a freshly fetched `origin/<base>`:
   - `ahead_by` = `git rev-list --count origin/<base>..<ref>`
   - `changed_files` = `git diff --name-only origin/<base>...<ref>`
     (three-dot diff, so changes that landed on `main` after the branch
     point are not counted)
   - also report `unpushed` = `git rev-list --count origin/<branch>..<ref>`
     (or `ahead_by` when origin has no branch), in the result dict, so the
     report shows when the merger rescued local-only work.
   Anything it cannot measure stays `(None, None)`, i.e. "don't know".
3. **Open the PR** with the existing `pe.create_pr`. It already pushes the
   local branch (`git push -u origin <branch>`, no force). If the push is
   rejected, `gh pr create` fails and the existing `pr_not_created` skip
   records it. **Never force-push.**

This is the root-cause fix for the five stranded tasks. On the shared-mount
path, the build never pushes its own branch
(`apps/backend/core/workspace_fetch.py:89` is a no-op without
`WORKSPACE_URI`). The only push was inside `pr_endgame`, which runs only on
the clean-completion path. Changing the merger instead of the build means
one push path covers both build backends and every existing branch.

### 2. The task status follows the PR

New `merger._sync_status(spec_dir, action)` writes through the existing
single writer `services/task_control.write_control` with
`updated_by="merger"`. Rather than adding new top-level `TaskStatus` values,
it adds `ReviewReason` values. The status model already has `done`,
`human_review` + `reviewReason`, and `plan_review` as a reason. That keeps the
approved names without editing every consumer of `TaskStatus`.

| merger action | written |
|---|---|
| `opened`, `already_open` | `human_review` / `awaiting_merge` (new) |
| `merged` | `done`, reviewReason cleared |
| `closed` | `human_review` / `pr_closed` (new) |
| `no_content` with no PR | `human_review` / `no_work` (new) |
| any other skip (unmeasurable, etc.) | unchanged |

**Only tasks whose current status is `human_review` are written.** A task
that a human moved, or that is `in_progress`, `backlog` or `done`, is never
touched. The merger never overwrites a human decision. `plan_review` already
exists and means "plan awaiting approval", so the merger never writes it.

Frontend: `apps/frontend-web/src/shared/types/task.ts` extends the
`ReviewReason` union with the three values. `components/TaskCard.tsx`
`getReviewReasonLabel` gets three cases with i18n labels: "PR open",
"PR closed", "No work produced". Today an unknown reason falls through to
`default: return null` (no badge), so the backend can ship first without
breaking the UI.

The merger's report gains `merged`, `closed` and `status_written` counts.

### 3. Call the merger at the end of every completed build

`services/completion_orchestration.run_terminal_completion` calls a new
`merger.process_one(project_id, project_path, spec_dir)`. That is the
existing `_process_spec` with `dry_run=False` plus `_sync_status`, run
through `asyncio.to_thread`. It sits after the PR endgame block, in its own
best-effort `try`, like its siblings, and runs **only when `is_completed`**.
A failed build is left to the periodic sweep, so a broken build does not
open a PR at once.

It runs after `run_pr_endgame` on purpose. `run_pr_endgame` returns once its
PR exists, so the merger then sees `already_open` and only writes
`awaiting_merge`. When the endgame did not run (QA refused, auto-PR off for
the endgame, or no context), the merger is the path that pushes and opens
the PR. `AIFACTORY_AUTO_PR` still gates PR creation inside `_decide`, as
today.

### 4. Backstop sweep: an in-process loop, not a CronJob (differs from the approved intent)

The intent approved "a periodic CronJob sweep". Reading the code changed my
recommendation:

- The only trigger is `POST /api/maintenance/merger/run`, which requires the
  `member` role. No existing CronJob calls an AIFactory API with
  credentials. A CronJob therefore needs a new machine identity with write
  access to every project, and a secret to rotate.
- The web-server already runs four in-process loops with the same shape
  (`services/stale_reaper.reaper_loop`: env-gated, `asyncio.to_thread`,
  a failed tick never kills the loop, one JSON report line per tick).

So: add `merger.merger_loop(stop=...)` modelled on `reaper_loop`, started in
`server/main.py`'s lifespan next to the reaper, and gated by
`AIFACTORY_MERGER_SWEEP` (off by default, enabled in the factory-gitops
aifactory manifest). The interval comes from
`AIFACTORY_MERGER_SWEEP_INTERVAL_S` (default 900). Each tick calls
`sweep(dry_run=False)` plus status sync over every project, and logs the
whole report as one JSON line.

**Cost of this choice:** `job-watchdog` monitors CronJobs, not in-process
loops, so a dead loop would go unnoticed. Mitigation: the loop records
the time of its last completed tick in memory, and the existing
`GET /api/maintenance/merger` report returns it as `last_tick_at`, so a
stale loop can be seen and probed.
**If you want the CronJob anyway**, the alternative is set out under
"Alternatives rejected" below.

## Alternatives rejected

- **Make the build push its own branch on the shared-mount path** (extend
  `maybe_push_workspace_branch`). That fixes new builds only. The five
  stranded branches and any future push failure would still need the merger,
  and there would be two push paths to keep in sync.
- **New top-level `TaskStatus` values `plan_review` / `awaiting_merge`.**
  Every route, filter and board column that switches on `TaskStatus` would
  need editing. `plan_review` already exists as a `ReviewReason`, and the
  reason field already carries exactly this kind of distinction.
- **A Kubernetes CronJob calling the route.** Needs a new privileged
  machine credential (see Design §4). Revisit if the job-watchdog coverage
  outweighs the extra credential.
- **Open a PR for failed builds at build end.** Noise. The sweep already
  covers them, keeping today's behaviour.
- **Force-push when the local and origin branches have diverged.** That can
  destroy work. The merger records it as a skip and a human decides.

## Risks

- **Stacked branches duplicate merged content.** Task 002 was started from
  `origin/aifactory/001-…`, which was later squash-merged. Its PR will show
  001's changes again and may conflict. The PR is a review surface, so a
  human resolves it; the merger does not try to rebase.
- **Mass PR creation on first enable.** The first sweep opens PRs for the
  five stranded tasks and any other project's stranded branches. Mitigation:
  the enable step runs a dry run first and the report is reviewed before
  `dry_run=False`.
- **Status writes racing a human.** `write_control` is atomic, but
  "read status, then write" is not. A human drag landing between them could
  be overwritten once. The window is milliseconds; accepted.
- **Reusing a branch name after a merge.** If a task is re-run on a branch
  whose PR was merged, the lookup finds `MERGED` and opens nothing.
  Accepted: task branches are per-spec and not reused today.
- **`gh` rate limits.** One `gh pr list` per spec per tick. 19 specs every
  15 minutes is far below the limit; the interval is configurable.

## Verification

- Unit tests (injectable `runner`, no network), in `tests/test_merger*.py`:
  - a local branch with unpushed commits and an origin branch at base is
    `opened` (not `no_content`), and the report shows `unpushed > 0`
  - a MERGED PR on the head opens no PR, even when the local branch is ahead
  - a CLOSED PR opens no PR and writes `pr_closed`
  - a failed `gh pr list` stays unmeasurable
  - status is written only from `human_review`; `in_progress` and a
    human-set `done` are untouched
  - `process_one` is called at completion only when `is_completed`
  - mutation check: reverting the local-ref measurement makes the
    unpushed test fail
- Live, in the aifactory pod, `sweep(dry_run=True)` on the 19 tasks must
  report: 001, 004, 005, 006 `merged`; 003 `closed`; 011–018
  `already_open`; 002 and 007–010 `would_open` with `unpushed > 0`; 019
  `no_content`.
- After enabling it for real: five new PRs in `pfactory-friends-demo`, and
  every one of the 19 tasks showing the status from the table above in
  `task_list`.
- The loop logs one report line per interval, and `last_tick_at` in the
  GET report advances each interval.
