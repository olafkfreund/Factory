# Spec: Standing nightly evaluation

## Design

1. **Config** `benchmarks/nightly-config.json`: `tasks` (15 instance ids, a
   fixed stratified subset of `swebench-verified-50.json`: 7 django, 3 sympy,
   1 each sphinx, pytest, xarray, pylint, scikit-learn; easy and medium mixed),
   `max_tasks`, `per_task_token_cap` (4,000,000), `total_token_budget`
   (40,000,000), `timeout_min` (45 per task), `tier`, `regression_drop_tasks`
   (2), `prompt_globs` (relative to the AIFactory checkout), and the list of
   services whose commit is recorded.
2. **`scripts/benchmarks/provenance.py`** (pure stdlib): `collect()` returns
   - `models_configured`: role -> model id, read with `ast.literal_eval` from
     `DEFAULT_PHASE_MODELS` in the AIFactory checkout's `phase_config.py`
     (no import); roles in `NIGHTLY_MODEL_OVERRIDES` (JSON, documented as
     "must mirror the server's environment") win. These are aliases and
     intent, not proof of what ran.
   - `models_observed` (added per task by `nightly_eval`): every `model` string
     found in the task's `token_usage.json` / `COMPLETED.json`, best effort,
     `[]` when absent. A configured-vs-observed mismatch is shown in the report.
   - `prompt_hash`: sha256 over sorted (relative path, file bytes) of the
     files matching `prompt_globs`.
   - `commits`: service -> `git rev-parse HEAD` of each checkout given by
     `<SERVICE>_DIR` env vars, plus the Factory commit; a missing checkout is
     recorded as `null`, never guessed.
   - `label()`: `factory-pipeline-<first 8 of sha256(configured+prompt_hash+commits)>`.
3. **`MODEL_NAME` replaced**: `run_pipeline_task.py` gains `--model-name`
   (default: `provenance.collect().label()`), threaded into
   `build_prediction_record` and the meta sidecar. It also gains `--run-id`,
   which prefixes the AIFactory project name (`swebench-<run_id>-<instance>`):
   today a rerun reuses a project by name even when its path differs, so a
   run-scoped scratch root alone would hit the old project. On a `timeout` the
   driver best-effort calls `POST /api/tasks/{id}/stop` (the endpoint exists,
   `execution.py:939`) so a timed-out task does not keep consuming quota while
   the next one starts. The label is a safe filename
   so `evaluate.py` finds the harness report unchanged.
4. **`scripts/benchmarks/nightly_eval.py`**:
   - `run`: load config, collect provenance, make a unique `run_id`
     (`<UTC YYYYMMDDTHHMMSSZ>`), use run-scoped work dirs
     (`<results_dir>/work/<run_id>/{scratch,predictions.jsonl}`), fetch problem
     statements for the chosen ids from the HF datasets-server `/filter`
     endpoint (cached), run `run_pipeline_task.py` per task sequentially.
     The driver exits 2 for every non-`completed` status, but the baseline
     shows patches from non-completed tasks still resolve, so exit 2 does not
     skip scoring: the prediction (possibly empty) and sidecar are kept; a
     driver crash with no sidecar is recorded as `driver_error`. Before each
     task, if cumulative tokens already reach `total_token_budget`, remaining
     tasks are recorded `skipped_budget` (the budget is a stop between tasks,
     not a ceiling: the last task may overshoot). A task whose tokens exceed
     `per_task_token_cap` is flagged `over_cap`; a task with no token evidence
     counts as `per_task_token_cap` toward the budget. Then run `evaluate.py`
     over the produced predictions with `--run-id <run_id>`, read the
     harness report id lists, and write `<results_dir>/<run_id>.json`.
   - `compare`: the previous run is the newest result file with a smaller
     `run_id`. The compared set is the tasks both runs scored (neither
     `skipped_budget`, `driver_error` nor harness-error). Regression =
     resolved count on that set falls by `regression_drop_tasks` or more, with
     at least `min_paired` (10) paired tasks; otherwise report "insufficient
     coverage" and do not alert. The report lists flips both ways, cost and
     duration deltas, and warns when the task lists or `prompt_hash`
     differ. Exit 3 on regression, 0 otherwise. A first run has no previous.
   - `report`: markdown time series (run id, resolved/scored, tokens, cost,
     wall time, label) over all result files, plus a baseline row computed from
     the 2026-07 baseline outcomes for the same 15 ids (stored in config as
     `baseline`), not the 19/50 figure.
   - Pure functions (`select_tasks`, `build_result`, `compare_results`,
     `render_report`) are unit tested, including driver exit 2 with a patch,
     driver crash, budget stop, harness errors and coverage gates.
5. **Storage**: `NIGHTLY_RESULTS_DIR` (default `~/.factory-bench/nightly`) on
   the runner, one JSON per run, also uploaded as a workflow artifact (90 day
   retention). The previous run is read from that directory, so the series
   survives runs without needing repo commits.
6. **Workflow** `.github/workflows/bench-nightly.yml`: `workflow_dispatch`
   enabled; the `schedule` trigger is present but commented out with the
   enable steps, because it needs the owner's runner. `runs-on: [self-hosted,
   factory-bench]`, `timeout-minutes: 720`, `concurrency` group so runs never
   overlap, steps: checkout, run, compare, report to the job summary, upload
   artifact, open or refresh an issue labelled `bench-regression` on exit 3
   (same github-script pattern as `parr-regression.yml`).
7. **Cost**: baseline averaged $1.15 and 2.37M tokens per task (heavy tail 12.5M
   tokens). 15 tasks is about $17 and 36M tokens a night on average (about
   $520 a month); the 40M-token budget stops new tasks past that point; the baseline ran on
   the subscription OAuth, so this draws quota rather than an API bill. This
   estimate goes in `docs/benchmarks/nightly-eval.md` for the owner to agree
   before enabling.
8. **Docs** `docs/benchmarks/nightly-eval.md`: what runs, the record format,
   the enable steps and what the owner must provide.

Known limits (stated in the doc): the per-task token cap is checked after the
task, not enforced mid-run (the pipeline has no token ceiling); the real
in-run bounds are task count, the per-task timeout with a best-effort stop, and
the total budget check between tasks. **Completion of the issue's first
criterion needs the owner**: the workflow lands with the schedule disabled; a
successful scheduled run is remaining work after the owner provides the runner
and agrees the cost.

## Alternatives rejected

- Run on `ubuntu-latest` against the deployed fleet: the driver needs a local
  scratch repo path visible to AIFactory and Docker for the harness.
- Commit results to the repo or a data branch: noisy history, needs write
  tokens; a runner directory plus artifact is enough for a first version.
- Import `phase_config` for model ids: pulls the AIFactory dependency tree
  into a Factory script; `ast.literal_eval` of one dict is enough.
- Per-service version endpoints for commit SHAs: none exist in a uniform
  form; the checkout used to run is the honest source.

## Risks

- Nightly cost drift: bounded by config and the budget stop.
- Flaky harness infrastructure errors (Docker read timeouts, see baseline)
  look like regressions: harness-error tasks are reported separately and
  dropped from the paired set on both sides.
- `models_configured` can differ from what ran (aliases, fallback, routing):
  hence `models_observed` and the mismatch line.
- Prompt hash only covers AIFactory prompts named in `prompt_globs`; prompts in
  other services are added by extending config.

## Verification

  report rendering (`scripts/benchmarks/test_nightly_eval.py`,
  `test_provenance.py`), updated `test_run_pipeline_task.py`.
- `ruff check`/`ruff format --check` and mypy as the repo CI does.
- `python3 scripts/benchmarks/nightly_eval.py run --dry-run` prints provenance
  and the task plan without calling anything.
- Workflow YAML parses; the schedule is not active (owner enables it).
