# Spec: Factory E2E test campaign

This design merges three independent proposals (Codex gpt-6.2-sol; agy, model not reported; Fable), then revises them after a Codex and agy review of the first draft. Code facts below were checked against origin/main, and against dev where the route is newer.

## Design

### 1. Harness

`scripts/e2e/` is a new package. It reuses only helpers from the existing scripts; their flows are not reused:
- **From `scripts/parr_regression.py`:** HTTP and auth helpers and the seam checks.
  - **Never use `--full`.** It selects `aifactory-demo` by substring (lines 339–376).
  - Its in-memory cleanup is not used either, because it swallows failures and cannot delete PFactory sessions.
- **From `scripts/benchmarks/run_pipeline_task.py`:** the poll and diff helpers only. Its flow is not reused: it clones a local scratch repo and calls `/from-issue`, while the campaign drives remote `Freundcloud/e2e-*` repos through `/from-plan`.
- **Reporting:** `scripts/e2e/report.py` reads the record format of `scripts/benchmarks/report.py` and adds:
  - `surface`, `project`, `stage_results` and `billing_mode`;
  - a **hidden-verdict-aware** median cost per accepted build.

  The original `backend_table` cannot do this: it sums cost over all runs and expects a SWE-bench eval report.

**A journey** = project × surface (`cli`, `mcp`, `ui`) × model × repeat. Stage runners S1–S5 and X call a surface adapter:
- `cli`: runs `factory …` as a subprocess;
- `mcp`: a stdio client to `factory mcp`;
- `ui`: Playwright, reusing the Keycloak/TOTP login from `TFactory/portal_testing/run.py`.

**Read-back** must use a **different code path**: the factory's REST API or its remote MCP (`aifactory.*`, `pfactory.*`, `cfactory_*`), plus the GitHub API. `factory mcp` shares handlers with the CLI, so a read through it does not count as independent.

**Hosts:**
- the owner chose `*.freundcloud.org.uk` (2026-11-24);
- the harness pins the resolved hosts explicitly and ignores CLI env and config overrides (`factory_cli/config.py:21-26,90-107`);
- the hosts are recorded in `run.meta.json`.

### 2. Safety: a registry of what the campaign created

The registry is the only mutation boundary.

- **The registry.** `evidence/<campaign>/registry.jsonl` is an append-only file. It is written **before** a create returns and records immutable IDs:
  - the GitHub repo `node_id`, `id` and `full_name`;
  - the factory project IDs per service;
  - the PFactory session ID;
  - the AIFactory task ID;
  - the TFactory spec ID;
  - the CFactory card key.

  Every mutation goes through `guard.py`. That covers start, approve, reject, move, run, archive, delete and teardown, and every factory, not just GitHub. **A mutation is refused unless:**
  - the target's immutable ID is in a registry, and
  - a live re-read shows it still belongs to that registry entry: the same repo `node_id`, or a project or card whose repo is the registered one.
- **GitHub.** Repos are created with the agenix `api-github-token`, as the owner decided. It is a broad classic PAT (`repo`, `delete_repo`, `admin:org`; admin on Freundcloud). On top of the registry, the guard also requires all of:
  - the owner is `Freundcloud`;
  - the name matches `^e2e-\d{8}-P[1-5]-\d+$`;
  - the repo has the topic `factory-e2e`.

  The token is read from its file at runtime and never logged.
- **Sweeper.** It deletes **registry entries only**: those from aborted or crashed campaigns that are more than 7 days old. Repos that match the name and topic but are in no registry are **reported, never deleted**. Each delete is followed by a read that confirms the resource is gone. PFactory sessions have no delete endpoint, so they are closed and recorded as retained. Dry-run is the default.
- **Factory isolation.**
  - A dedicated org, `factory-e2e`, is used in **AIFactory, PFactory and TFactory**. All three issue org-scoped `acw_` keys (AIF/PF/TF `routes/api_keys.py`). TFactory's MCP filters project listings by the caller's visible project IDs (`mcp_stdio/router.py:148-162`).
  - **CFactory** keys (`CFACTORY_API_KEYS`) have a global read/write scope and no project scope (`auth.py:83-90`). So **CFactory writes go through the registry guard only**: every card write is checked against the registered card key and repo.
  - Multi-tenancy (`*_MULTI_TENANT`: AIF/PF `tenancy.py`, TF `routes/_tenancy.py`, CF `api_deps.py:54-76`) is off on prod and stays off. Step 0 confirms this from the deployed config.
- **Key scopes.** A `mcp:read`/`mcp:write` key is rejected by REST (`authenticate_rest` requires the `api` scope, `mcp_remote/auth.py:120-130`). Writes under `/api/mcp-stdio` need `project:write`, `task:write` and `task:merge` (`mcp_stdio/auth.py:18-21`). Step 0 mints keys with exactly the scopes the harness uses, then runs an **authorization preflight**: one read and one dry write per operation. A journey starts only after the preflight passes.

### 3. Model selection

- **How the model is set.** `/from-plan` (`create_from_trusted_plan`, `execution.py:1362+`) ignores `request.model`. The model comes from the **signed plan's `execution` block**, through `ingest_trusted_plan`. So the model sweep sets the coder and reviewer models **in the fixture plan's execution profile**: `phaseModels` gives the coder and the QA reviewer different models. That plan is then signed and ingested.
- **Step 0 probe.** It runs this real signed-plan path with Codex and Gemini profiles, and must get **runtime evidence** of the provider and model for both coder and reviewer: worker logs or usage records with a model field. Request echo or `token-usage` alone does not count. If the provider is not routed, an AIFactory change adds it to the execution profile. That change is its own issue and release, and it gates step 4.
- **PFactory planning and TFactory** stay on their default profiles; their model is recorded but not swept.

### 4. Fixtures

They live in `tests/e2e/fixtures/P1..P5`. Each fixture has:
- a starter tree;
- an intent/spec/plan triple with the execution profile;
- a reference solution;
- a hidden acceptance suite in `tests/e2e/hidden/`, which is never pushed to the test repo.

| ID | Project | Size | Purpose |
|---|---|---|---|
| P1 | Python stdlib CLI `wordfreq`, pytest | XS | Canary |
| P2 | TypeScript Express API, jest, 3 endpoints | S | Model sweep |
| P3 | Go service plus a React page | M | Parallel waves, browser lane |
| P4 | Brownfield: a planted bug, a failing test, an ambiguous requirement | S | Gates, handback, mutant |
| P5 | Trap: a contradictory criterion | XS | Must end in Needs you |

### 5. Matrix: 19 journeys

| Slice | Journeys | n | Cap per run |
|---|---|---|---|
| Surface sweep | P1 × {cli, mcp, ui} × Claude × 2 repeats | 6 | $15 / 60m |
| Model sweep | P2 × cli × {Claude, Codex, Gemini} × 2 repeats | 6 | $15 / 60m |
| Depth | P3 × mcp × {Claude, Codex} | 2 | $25 / 90m |
| Brownfield | P4 × ui × {Claude, Gemini} | 2 | $25 / 90m |
| Negative | P5 × {cli, ui} × Claude | 2 | $15 / 60m |
| Rules ablation | P1 × cli × Claude, rules and skills off | 1 | $15 / 60m |

**"Twice" means all three of these:**
- a repeat run (P1 and P2), or a paired run (P3 and P4 pair models; P5 pairs surfaces);
- read-back through an independent path;
- the hidden suite run on the merge SHA.

**Known gaps:**
- Surface and model are never crossed on the same fixture.
- P3 has no Gemini run, P4 has no Codex run, and P5 runs Claude only.

These gaps are published with every report.

**A UI result that disagrees with the read-back is a surface failure.** It is recorded, never suppressed.

### 6. Stage oracles and must-fail probes

Each probe has a controlled input and an **expected, specific failure reason**. An auth error, a missing route or an infrastructure error never satisfies a must-fail probe.

**S1 Onboard**
- **Pass:** the registered repo exists with branch protection; there is one project per service in the e2e org; there is exactly one CFactory card for that repo.
- **Probes:**
  - Replay onboarding: still one project and one card.
  - Onboard a registered repo that the key cannot reach: an explicit access error.

**S2 Plan**
- **Pass:** `POST /api/mcp-stdio/plan/sessions/ingest-approved` (PFactory dev, 0.9.4) accepts the triple, then approve, then emit, and AIFactory `/from-plan` accepts the signed plan. A review finding of at least one is required on P4 and P5.
- **Probes:**
  - Change one byte of an artifact but keep the original blob SHA: PFactory rejects it with the integrity reason.
  - Change one byte of the signed contract: AIFactory gives its signed-plan rejection.
  - Replay: the dedup response comes back and **no new AIFactory task** is created.

**S3 Code**
- **Pass:**
  - the task is terminal and green;
  - the diff is non-empty and touches only the plan's files, excluding `intent/`, `spec/`, `plan/` and lockfiles;
  - a review is recorded;
  - the runtime evidence shows the reviewer model differs from the coder model.
- **Probes:**
  - The diff is empty or docs-only.
  - Usage stays at zero after the usage deadline. `token-usage` returns an all-zero 200 until `token_usage.json` syncs (`tasks_usage.py:40-43`), so the harness polls until a deadline. "Missing usage" is a finding, not a stage fail.

**S4 PR**
- **Pass:**
  - the PR is merged by the pipeline: the merge actor comes from the PR timeline events and must be the service identity;
  - required checks are green on the head that was merged;
  - the PR links intent, spec and plan.
- **Probe:** push a commit to the PR head after the verdict. The merge must be refused as stale, and a fresh verdict must be produced on the new head before the merge.
- `check_merge_attribution.py` and `check_orphaned_pr_commits.py` are not used. Both hardcode `olafkfreund`, and the orphan checker skips open PRs.

**S5 TFactory**
- **Pass:** a verdict on the **merge SHA** with all 5 signals, and the hidden suite green on the same SHA.
- **Probes:**
  - A controlled SHA where tests are collected but are empty or skipped gives a specific "0 tests" reason.
  - A verdict-SHA mismatch is rejected.
  - **P4 mutant:** after the merge, a probe branch re-plants the bug and TFactory is run against that SHA. It must give a red verdict naming the failing behaviour. Auto-repair is disabled for the probe run.

**X Cross-factory**
- **Pass:**
  - The expected events (producer × phase × journey, legitimate handbacks included) all appear on that card's timeline, in order.
  - The journey's cost equals the sum of its stage usages within ±1%.
  - **No anomaly references a registered card key.** `cfactory_get_anomalies` and `cfactory_get_rollups` are global (`mcp.py:138-153`), so their output is filtered to the registry.
- **Probes:**
  - Re-deliver the same event ID: it is applied once (the store dedups by ID, `store.py:179-207`).
  - The CFactory#583 probe: two registered repos, each with issue #1. Their stage results must not bleed across.
  - The dropped-event probe is deferred until CFactory has a safe injection seam. This is recorded as a gap.

Every stage has a deadline. An acknowledgement without the expected state is a failure.

### 7. Cost and caps

- **Recorded per run:**
  - the requested model and the runtime model, for each phase;
  - tokens in, out and from cache;
  - `cost_usd` and `billing_mode`;
  - wall time, turns and handbacks;
  - the first-pass verdict and the hidden-suite result.
- **Sources:**
  - AIFactory `GET /api/tasks/{id}/token-usage`, which needs the `api` scope;
  - `CompletionEvent.usage` with `rollup_usage`;
  - CFactory `/api/tokens` and `/api/rollups`, filtered to the registry;
  - the provider or gateway log, where one exists.

  Drift above 5% is a finding. Subscription billing is reported as tokens only.
- **Caps are enforced remotely:**
  - before dispatch, the harness reserves the run's cap against the campaign budget;
  - at the cap, it calls the stop endpoint and **confirms** the task is terminal or stopped before releasing the lane;
  - a run whose stop cannot be confirmed blocks the next journey on that lane and is filed.
- **Campaign:**
  - $450 metered covers the 19 journeys: 14 × $15 + 4 × $25 + 1 × $15 = $325 at the caps, leaving $125 for probes and controls;
  - 3 concurrent lanes;
  - an 8-hour limit.
- **Build-out runs** (steps 0, 4, 5, 6 and 8) have their own caps, stated in each step. They are not part of the campaign budget.

### 8. Rules and skills audit

- **Were the rules followed?** Checked from git and transcripts:
  - artifact order;
  - conventional commits and attribution;
  - scope;
  - `Closes #N`;
  - no main pushes.
- **Are they effective?** The ablation journey runs with rules and skills off, and is compared with the P1 cli Claude run.
- **Are they consistent?**
  - CLAUDE.md, AGENTS.md and GEMINI.md are diffed across repos.
  - The P2 runs are scored on a 10-item checklist for each model.
- **Scorers:** Fable scores, and Codex second-scores 20%.

### 9. RFactory

RFactory roles come from the **email allowlists** (`RFACTORY_ALLOWED_EMAILS`, `RFACTORY_APPROVERS`, `RFACTORY_ADMINS`) checked against `x-forwarded-email` (`core/src/roles.js`, `web/server.js:96-98`). They do not come from Keycloak roles.

**Where it runs:**
- an **isolated** campaign config directory and Claude home (not `~/.config/rfactory`), on a runner where the fixed `rfactory` pod name does not collide;
- writes disabled;
- it reads prod CFactory with an e2e read key.

**Role tests** run against `web/server.js` started directly on loopback, with a crafted `x-forwarded-email` for each role:
- an outsider is denied;
- a member can read;
- an approver and an admin each get a **role-specific observation**.

**One SSO check** goes through `deploy/pod.sh up` (oauth2-proxy) as `e2e-runner`.

**API checks:**
- `POST /api/standup` returns the buckets with no AI call. It is single-flight (409 when busy), so these calls are serialised.
- `GET /api/review/<card>` returns 404 for a known out-of-scope card and 200 for an in-scope control card.
- During a retained P1 journey, its card appears.

**CFactory#583:** probed with the two issue-#1 repos.

**Weekly:** a synthetic-meeting bot smoke.

**Prerequisites:** step 0 provides the files `pod.sh` needs, at mode 600:
- `scope.json`;
- `cfactory-read-key`;
- `keycloak-client-secret`;
- `oauth2-cookie-secret`.

It also provides the allowlists and a clean public commit (`source-guard.sh`).

### 10. Management

- **Tracking:**
  - the Factory epic #3882;
  - one issue per campaign, `e2e-campaign-YYYY-MM-DD`;
  - one child issue per failure, labelled `e2e` and the stage;
  - the report is posted on the campaign issue.
- **Evidence:**
  - Actions artifacts, kept 30 days, after gitleaks;
  - the registry is part of the evidence.
- **Roles:**
  - **Claude** leads, runs the MCP surface, triages and merges.
  - **Codex** builds the harness and the AIFactory/PFactory/CLI changes, runs the CLI surface and the hidden suites.
  - **agy** builds the UI runner and the fixtures, and runs the UI surface.
  - **Fable** reviews the oracles, runs the rules audit and adjudicates.

  The reviewer of a stage is never the model that built it.
- **Triage** sorts each failure into one of four classes:
  - product bug (blocks a release);
  - surface gap (blocks a release);
  - model or skill drift;
  - infra or flake (needs 2 reproductions).
- **Cadence:**
  - nightly: the seam gate, plus P1 on cli;
  - weekly: the campaign;
  - on a model or release change: the model sweep.

## Alternatives rejected

- **The full cube (90 runs):** over budget for little extra.
- **A staging namespace:** the owner chose prod.
- **A sweeper keyed on name and topic only:** it can delete a repo it did not create. It is replaced by the registry.
- **`parr_regression --full` and the benchmark flow:** they target `aifactory-demo` and local repos.
- **Reading back through `factory mcp`:** it shares handlers with the CLI, so it is not independent.
- **Ollama:** excluded by the owner.
- **AIFactory `POST /repos`:** it uses the server's gh login.

## Risks

- **The harness mutates real resources.**
  - The broad PAT and the unscoped CFactory write key make this the top risk.
  - Mitigation: the registry guard on every mutation, with a live identity re-check, plus refusal tests for every service.
- **Cost overrun.**
  - Mitigations: spend reservation, confirmed stop, the caps, and XS fixtures first.
- **Flakiness.**
  - Mitigations: the hidden suites and specific failure reasons serve as oracles; there is one infra retry.
- **A shared-host collision (RFactory pod).**
  - Mitigations: an isolated config and runner, and a post on the bus first.
- **Prod drift.**
  - Mitigation: step 0 confirms the deployed revisions (PFactory 0.9.4 with `ingest-approved`) and the tenancy flags before any journey.

## Verification

- **The campaign checks itself.** It is red if any of these fails to happen:
  - P5 stops;
  - the P4 mutant goes red;
  - both tamper probes are rejected with their specific reasons;
  - read-back agrees.
- **The cap test:** a $0.01 cap on one P1 run must abort the run, and the harness must **confirm the remote task stopped**.
- **Guard refusal tests:** each service's guard must refuse:
  - a real repo (`Freundcloud/Factory`);
  - another org;
  - a missing topic;
  - a malformed name;
  - an unregistered project or card;
  - a registered ID whose live re-read no longer matches.
- **The sweeper's first live run** comes only after its dry-run list has been checked by hand.
