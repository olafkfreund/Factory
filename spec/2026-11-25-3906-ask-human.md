# Spec: factory coders can ask the user mid-build

Revision 2 follows the Codex and agy spec reviews. The main changes:

- **Pause:** the pause is now owned by the runner and confirmed by the
  control plane, and the work is saved before pausing.
- **Answers:** one durable answer per question, with retried delivery.
- **Approval:** approval needs an interactive portal session, checked on the
  server.
- **Guards:** the merger and CFactory leave a paused task alone.
- **Bus:** posts on the bus carry no content.

## Facts this design builds on

AIFactory `origin/dev` `9962aaa8`, CFactory `origin/dev` `7bcf672f`.

- **Tools.**
  - Coder tools are registered in `tools_pkg/registry.py:33-86` and listed
    in `models.py:51-72,190-200`.
  - The standalone MCP server imports `create_all_tools`
    (`mcp_server/aifactory_server.py:135-164`).
  - Non-Claude coding providers do not get `tools_pkg` tools.
- **Sessions.** A tool result is consumed inside the session. Post-session
  processing, recovery and QA run after it (`session.py:510-668`,
  `coder.py:658-682,880-1018`, `build_commands.py:612-617`).
- **How a pause is recognized today:**
  - **Local:** `process_monitor.py:418-499,777-794` reads
    `review_state.json`.
  - **Kubejob:** the reaper calls `_pause_confirmed` after an allowlist check
    (`agent_kubejob.py:76-150,336-374`). An unconfirmed claim becomes a
    terminal completion and a TFactory hand-off.
- **Workspaces.**
  - **Local isolated builds** reuse the registered worktree
    (`workspace/setup.py:264-282`).
  - **Kubejob** deletes and re-clones (`build_backend.py:1428-1472`).
    Packed `/work` is ephemeral, and the push keeps committed branch state
    only (`workspace_fetch.py:106-185`).
- **The inbox.**
  - Startup copies the source spec dir into the worktree
    (`workspace/setup.py:205-221`).
  - The drain marks the localized copy as read (`agents/inbox.py:126-145`).
  - The inbox route may target an old worktree (`routes/inbox.py:86-114`).
- **Authentication.**
  - An `acw_` key with `api` scope resolves to its owner through
    `get_current_user`.
  - Portal JWTs come from both OIDC and local login, in a cookie or a bearer
    header (`auth.py:215-392`, `auth_routes.py:97-178`).
  - `request.state.user` carries `api_key_id`, `scoped_service`,
    `is_legacy_shared_token` and `is_service`.
- **The merger** can rewrite any `human_review` to `no_work`,
  `awaiting_merge` or `done`, and can open a PR
  (`merger.py:310-456,557-568`). Its sweep is optional, every 15 minutes
  (`:601-676`).
- **CFactory** drops `reviewReason` (`adapters/aifactory.py:39-52`) and
  shows generic approve and reject actions that can lead to a PR and a merge
  (`TaskActions.tsx:63-71`, `actions.py:196-225`).
- **`factory_common.secrets.redact`** replaces only recognized secret
  patterns.

## Design

### D1. `ask_human` and a pause owned by the runner (AIFactory)

**The tool.**

- `ask_human` is registered for the **Claude coder session only**: in the
  coder client's tool list (`core/client.py:950`), **not** in
  `create_all_tools`, so the standalone MCP server never exposes it.
- It is out of scope for non-Claude coding providers, which carry on as
  today.

**Arguments:**

- `question` (required);
- `choices` (optional, 2-6);
- `needs_approval` (bool);
- `context` (the plan step and files);
- `default` (optional suggestion, shown and never applied);
- `timeout_minutes` (default 30, at most 1440).

**What it writes.** It writes `questions/<qid>.json` into the worktree spec
dir, with:

- the question, choices, `needs_approval`, context and default;
- `status: "open"`, `asked_at`, `asked_by_model`, `run_id`.

It then returns: "Question recorded. Stop now: end your turn without further
changes."

**Limits.**

- At most 3 questions per run (one start or resume) and 10 per task.
- Past either limit, the tool returns an error telling the coder to proceed
  on its best reading or stop.

**The pause** is owned by the runner, in the coder's post-session turn loop
(`coder.py` ~880-1018), right after `run_session_guarded`. When the worktree
has an open question from this run, the runner does these steps in order:

1. **Saves the work.** It commits work in progress to the task branch
   `aifactory/<spec>` with the message `wip: paused for question <qid>`, and
   pushes it the way the packed path pushes. This is the checkpoint for
   resume.
2. **Moves the question to the control plane.**
   - **Local:** it copies `questions/` into the source spec dir.
   - **Packed:** it uploads with `push_questions`, a new per-run helper in
     `workspace_fetch.py`.
3. **Records the pause.** It writes `review_state.json` with
   `reason: "needs_input"` and the `qid`. It sets the plan to `human_review`
   with `reviewReason: "needs_input"` and syncs that to the source.
4. **Returns.** Subtask recovery, QA, finalization and auto-continue are all
   skipped. `build_commands.py` (~612) does not run QA while a
   `needs_input` pause is in place.

**The control plane confirms the pause.**

- **Local:** `process_monitor.py` gains a `needs_input` branch. It neither
  auto-continues nor completes, emits `human_review/needs_input`, and
  releases the slot.
- **Kubejob:** `needs_input` joins `_REVIEW_PAUSE_REASONS`, and
  `_pause_confirmed` confirms it only if `fetch_questions` returns an open
  question for this run. Without one, it is a normal completion, as today.
- **Status writes:** `task_control.write_control` and `_update_plan_status`
  keep `reviewReason` as `needs_input`.

**The coder prompt** gets a short rule. Ask when:

- requirements are ambiguous or contradict each other;
- a change falls outside the plan's files;
- a change is destructive or irreversible.

Never ask about anything the plan or the repository already answers.

### D2. One durable answer, retried delivery, resume (AIFactory)

**The question file.** The control-plane copy of each question,
`source_spec_dir/questions/<qid>.json`, is the only record. An answer
updates it under a file lock, and only from `open` or `expired` to
`answered`. A second answer gets `409 already answered`.

**Routes:**

- `GET /api/tasks/{id}/questions`;
- `POST /api/tasks/{id}/questions/{qid}/answer` with `{answer}` or
  `{decision: "approve" | "reject", note}`.

  The `qid` must belong to that task. When the question has choices, the
  answer must be one of them.

**Authorization.**

- **Role:** project member or higher.
- **Approval questions** accept only an interactive portal session. The
  check:
  - `request.state.user` comes from a JWT, with no `api_key_id`,
    `scoped_service`, `is_legacy_shared_token` or `is_service`;
  - the JWT arrived **in the cookie**, not in a bearer header;
  - the request carries a one-time `confirm_token`, which the portal fetches
    from `GET /questions/{qid}/confirm-token` (also cookie-only, valid for 5
    minutes, bound to user, qid and session).

  Anything else gets `403 approval requires a person in the portal`.
- **The limit,** which is recorded: a script holding the user's browser
  cookie could still pass. Proving a person clicked is not possible with
  today's login. This blocks every agent path that uses keys.
- **The audit fields** come from the request context, not from the body:
  `answered_by` (user id), `channel` (`portal`, `mcp` or `cfactory`),
  `auth` (`session` or `key:<id>`) and `answered_at`.

**Rejecting an approval** marks the question `rejected`. The task stays
paused, with `reviewReason: "approval_rejected"`, and does not resume. A
user can archive it, or retry it with new instructions, through the existing
actions.

**Delivery and resume.**

- The answer is written into the **source** spec dir inbox
  (`source_spec_dir/inbox/agent.json`, not the route's worktree target),
  with `qid` and `answer_id`.
- The question gets `delivery: "pending"`, and the build is started through
  the existing start path.
- When the launch succeeds, the question becomes `delivery: "launched"`.
- When the launch fails, it stays `pending`, and the question checker (D6)
  retries it with backoff.
- The drain marks a message read in **both** the worktree copy and the
  source copy, keyed by `answer_id`, so a later restart cannot replay it.

**Resume per backend.**

- **Local:** reuses the registered worktree, so the work in progress is
  already there.
- **Kubejob:** the dispatcher clones and checks out the existing task branch
  `aifactory/<spec>` (the WIP checkpoint from D1) instead of the base tip.

**Guards.** Plain start and recover are refused with 409 while an approval
question is open or rejected. The answer route is the only way to resume
past it.

### D3. MCP tools for terminals (AIFactory)

**`aifactory.questions_pending`** (`mcp:read`).

- It takes no `task_id`. Remote dispatch gets an explicit no-task path that
  filters by the projects the key's user can see.
- It lists `open` and `expired` questions with id, task, project, text,
  choices, `needs_approval`, age and the portal link.

**`aifactory.answer_question`** (`mcp:write`).

- It requires `task_id` and `qid` and calls D2.
- An MCP-only personal key works through the scoped proxy path.
- **Ownerless and legacy shared keys** get a refusal.
- **Approval questions** get a refusal plus the portal link.

Both tools exist in remote MCP and mcp-stdio.

### D4. Content-free bus notices (AIFactory)

**What is posted.** `services/bus_notify.py` posts **only**: `[factory] a
question is waiting for you — run aifactory.questions_pending or open
<portal>/needs-input`.

- No question text, no project, task or repo name, and no answers.
- So posting to the shared `#agents` room exposes nothing that project
  access protects.

**Credentials and destination.**

- The bot token stays in the AIFactory control plane (a sealed secret), and
  is used only against the configured HTTPS homeserver.
- The owner creates the bot and the token.
- With no configuration, nothing is posted.

**For the reading agent.** The skill line tells sessions to treat the notice
as data, and to fetch the details through MCP, which applies project access.

### D5. Portals (AIFactory, CFactory)

**AIFactory task view.**

- A "Needs input" banner shows the question.
- A factual question gets choice buttons or free text.
- An approval question gets Approve and Reject, with `confirm_token`.
- The board shows `human_review/needs_input` as "Needs input", not as code
  review.
- Merge-review actions are hidden.

**CFactory.**

- The AIFactory adapter carries `reviewReason` and a `questions` summary
  through.
- When `reviewReason` is `needs_input` or `approval_rejected`:
  - Needs you shows the question;
  - `approve_review` and `reject_review` are disabled;
  - the action is a link to the AIFactory task view.
- Answer buttons inside CFactory wait for #3905's user identity, and are out
  of scope here.

### D6. Question checker and expiry (AIFactory)

**A standalone loop.** The web-server lifespan gains its own periodic task
(every 60 s), not the optional merger sweep. It:

- marks overdue `open` questions `expired`, which stay listed and
  answerable;
- posts one D4 notice per expiry;
- retries `delivery: "pending"` launches.

**The merger guard.** `merger._process_spec` and `_sync_status` skip any spec
whose `reviewReason` is `needs_input`, `approval_rejected` or `plan_review`.
The same goes for explicit PR actions (`routes/pr.py`). Paused work never
opens a PR, and its status is never rewritten.

### D7. Proof in E2E (Factory)

- **P5** (the contradictory criterion) must end in an open `needs_input`
  question that cites the contradiction. That holds through at least one
  merger tick, with:
  - no PR and no TFactory hand-off;
  - the WIP checkpoint on the task branch.
- **A factual P1 variant** is answered over MCP and must resume and finish,
  carrying the exact answer through to the run.
- **The harness never answers approval questions.**

## Alternatives rejected

- **A tool that blocks inside the session.** It holds the slot and the
  session for hours, and the inbox is only read between turns.
- **A new status literal.** `reviewReason` reuses every existing classifier.
- **MCP server notifications.** Clients don't surface them as prompts.
- **Question text on the bus.** The shared room ignores project access.
- **Approval with any authenticated principal.** Personal keys resolve to
  the owner.
- **The before-build clarification flow.** It has no pending state, resume
  or identity.

## Risks

- **A cookie-holding script can still approve.** This is recorded as a known
  limit. Closing it needs step-up auth (a Keycloak re-auth or WebAuthn), a
  possible follow-up.
- **WIP commits on the task branch** before the PR: they are squashed by the
  existing PR flow. The PR shows the `wip:` commit only if the flow does not
  squash, and the plan checks which.
- **Kubejob resume from the task branch** relies on the push and checkout,
  which get new tests.
- **The question budget** limits spam; E2E measures it.
- **Hosts:** prod k3s through gitops only. No p510.

## Verification

**AIFactory unit and integration tests.**

- **The tool:** absent from the standalone MCP server; question budgets.
- **The pause, local:** an open question leads to the WIP commit, questions
  synced, `review_state` written, no QA, no auto-continue, and
  `human_review/needs_input` emitted.
- **The pause, kubejob:** `_pause_confirmed` accepts with a fetched open
  question and refuses without one, and the refusal leads to normal
  completion.
- **Answering:**
  - one answer per question, so a second answer gets 409;
  - an answer racing expiry;
  - a launch failure leading to a retry;
  - replay safety after a restart;
  - a rejected approval keeping the task paused;
  - start and recover refused while an approval is open.
- **Approval identity:**
  - refused with 403: an `acw_` key, a scoped key, the legacy token, and a
    bearer JWT;
  - accepted: a cookie session plus `confirm_token`.
- **Resume:** local in the same worktree; kubejob checks out the WIP branch;
  the coder receives the exact answer.
- **The merger:** a tick on a paused branch with commits opens no PR and
  rewrites no status.
- **MCP:** both transports; a pending list scoped across two projects; a
  `qid` from another task is refused.
- **The bus:** the notice carries no content; skipped when unconfigured.

**CFactory tests:** `reviewReason` is carried through; approve and reject
are disabled; the question is shown.

**Live E2E:** P5 and the P1 variant as in D7.
