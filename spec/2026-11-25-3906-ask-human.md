# Spec: factory coders can ask the user mid-build

## Facts this design builds on

AIFactory `origin/dev` and CFactory, read on 2026-11-25:

- **Coder tools** are `@tool` functions in
  `apps/backend/agents/tools_pkg/tools/`. They are registered in
  `tools_pkg/registry.py:33-86` and allowed for the coder in
  `tools_pkg/models.py:51-72,190-200`. No tool blocks.
- **The inbox** is `<spec_dir>/inbox/<recipient>.json`.
  - It is written by `services/inbox_service.enqueue` (flock).
  - Its route is `POST /api/tasks/{id}/inbox`.
  - The coder drains the `agent` inbox once per turn (`coder.py:747-759`).
- **There is a pause precedent.** At `coder.py:572-618`, the coder sets the
  plan to `human_review` with a `reviewReason`, then returns. The kubejob
  path accepts only the reasons listed in `_REVIEW_PAUSE_REASONS`
  (`agent_kubejob.py:110-146`).
- **There is no `needs_input` status.** `reviewReason` is a free string
  (`task_models.py:146`).
- **MCP.**
  - Remote tools are listed in `mcp_remote/tools.py` (`get_tool_definitions`,
    `_SCOPE_FOR_TOOL`).
  - The scopes are `mcp:read` and `mcp:write`.
  - A key with no user is a service principal (`auth.py:202-226`). Human web
    users come through `get_current_user`.
- **CFactory Needs you.**
  - It already counts any stage in a review status (`needs_you.py:25-35`).
  - Its view has no answer actions.
  - Its AIFactory adapter only reads.
- **No code posts to the Matrix agent bus** today.
- **Redaction:** `factory_common.secrets.redact`.

## Design

### D1. The `ask_human` tool and the pause

**The tool.** A new coder tool, `ask_human`, lives in
`tools_pkg/tools/human.py`. It is registered in `registry.py` and listed for
the coder in `models.py`. Its arguments:

- `question` (required);
- `choices` (optional, 2-6);
- `needs_approval` (bool);
- `context` (the plan step and files);
- `default` (optional: what happens if nobody answers).

**What it writes.** It writes `questions/<qid>.json` in the **source** spec
dir. The coder can only read that dir, as with #2233's evidence. The file
holds:

- `qid`, the question, choices, `needs_approval` and context;
- `status: "open"`, `asked_at`, `asked_by_model`;
- the task's project id.

The text is run through `redact` first.

**The pause.**

- The tool returns "question recorded; the build will pause". The coder
  then ends the session.
- At the next turn boundary, the loop sees an open question, sets the plan
  status to `human_review` with `reviewReason: "needs_input"`, and returns.
  This is the same path as `plan_review`.
- `needs_input` is added to `_REVIEW_PAUSE_REASONS`.
- No process or build slot is held while it waits.

**No new status literal.** `human_review` plus `needs_input` keeps every
existing board, merger and CFactory classifier working. The UI labels it
"Needs input".

**Limits.**

- A task may ask at most **3** questions per run. A fourth call returns an
  error telling the coder to proceed or stop.
- The coder prompt (`prompts/coder*.md`) gets a short "when to ask" rule:
  - **Ask when:** the requirement is ambiguous or contradictory; a change
    falls outside the plan's files; or the change is destructive or
    irreversible.
  - **Never ask about:** anything the plan or repository already answers.

### D2. Answering, and resuming

**Routes.**

- `GET /api/tasks/{id}/questions` lists the questions.
- `POST /api/tasks/{id}/questions/{qid}/answer` with `{answer}` answers
  one. The answer must be one of `choices` when choices were given.

**Authorization.**

- Answering needs project role **member** or higher (#2182 and #3905).
- **Approval questions** (`needs_approval: true`) accept an answer only from
  an interactive human session: `get_current_user`, a Keycloak cookie or
  bearer from the portal.
- Every API key, including a user's personal acw key used by an agent, gets
  `403 approval requires a person`.

**The answer.**

- It is written to the question file: `status: "answered"`, `answer`,
  `answered_by` (user id, or key id plus "agent"), `channel` (`portal`,
  `mcp` or `cfactory`) and `answered_at`.
- It is enqueued in the `agent` inbox as "Answer to <qid>: …".
- The route then restarts the build through the existing start path, in the
  same worktree.

**Resuming.**

- The coder drains the inbox at its next turn and continues.
- If the start path cannot reuse the worktree (unverified for kubejob;
  checked in the plan), the resume falls back to `recover` with
  `auto_restart`. The answer still reaches the coder through the inbox file
  in the source spec dir.

### D3. MCP tools for terminals

**Remote MCP** (`mcp_remote/tools.py`) and **mcp-stdio** get two tools:

- **`aifactory.questions_pending`** (`mcp:read`) lists open questions for
  projects the key's user can see. Each entry gives the id, task, project,
  text, choices, `needs_approval`, age and the portal link.
- **`aifactory.answer_question`** (`mcp:write`) calls D2. For a
  `needs_approval` question it refuses and returns the portal link, so the
  terminal shows "approve here: <link>".

Claude, Codex and agy already load these servers, so no client change is
needed.

### D4. Push to the terminal over the agent bus

**The service.** AIFactory gains `services/bus_notify.py`.

- **When it posts:** when a question opens, when it times out, and when it is
  answered.
- **Where it posts:** the Matrix client-server API (`PUT
  /_matrix/client/v3/rooms/{room}/send/m.room.message/{txn}`), into the
  `#agents` room.
- **What it posts:** one redacted line of the form `[factory question]
  <project>/<task> <qid>: <question> — answer: aifactory.answer_question
  qid=<qid> | <portal link>`.

**Configuration.**

- `AIFACTORY_BUS_HOMESERVER`, `AIFACTORY_BUS_ROOM` and a bot access token
  (sealed secret).
- The bot account and token are created by the owner. Agents never create
  them.
- When the configuration is absent, posting is skipped, and MCP and the
  portal still work.

**How terminals pick it up.** Claude Code sessions already read the bus
through the `agent-bus` MCP (`read_new`). The skill text gets one line: on a
`[factory question]`, show it to the user.

### D5. The portals show the question with answer actions

**AIFactory task view.** A "Needs input" banner shows the question and the
choice buttons or a free-text box, and posts to D2. Approval questions show
"Approve" and "Reject" for a human session.

**CFactory Needs you.**

- The work item already appears there, because the stage is in review.
- A new read through the adapter (`GET /api/tasks/{id}/questions`) shows
  the question text.
- **Factual questions** get answer buttons that call AIFactory D2 through
  a new adapter write. It carries the CFactory user's identity once #3905
  gives CFactory user identity. Until then the buttons are a link to the
  AIFactory task view.
- **Approval questions** always link to the AIFactory task view.

### D6. Timeout

**The timeout.** Each question carries `timeout_minutes`: 30 by default,
1440 at most.

**What happens.** A periodic check in the existing merger sweep loop
handles it:

- the question becomes `status: "expired"`;
- a timeout line is posted to the bus;
- `reviewReason` stays `needs_input`, because "stop in Needs you" is already
  the paused state.

**A late answer.** An answer after expiry is still accepted, and it resumes
the task. Pausing holds no resources, so there is nothing to reclaim. If the
coder gave a `default`, it is shown as the suggested answer. It is never
applied automatically.

### D7. Proof in E2E (Factory)

**Fixture.** P5 (the contradictory criterion) must end with:

- an open `needs_input` question that cites the contradiction;
- no red build and no merged PR.

**Harness.** It reads `GET /api/tasks/{id}/questions` through the API and
answers through `aifactory.answer_question` for a factual P1 variant, to
prove that resume works.

**Safety.** The harness never answers approval questions.

## Alternatives rejected

- **A blocking tool that waits inside the session.** It holds a build slot
  and a model session open for up to 24 h, and the inbox is only read
  between turns anyway.
- **A new `needs_input` status literal.** It would touch the board, merger,
  kubejob, frontend and CFactory classifiers. A `reviewReason` reuses all of
  them.
- **Pushing through MCP server notifications.** Claude, Codex and agy don't
  surface unsolicited server notifications as prompts. Polling plus a bus
  push is reliable.
- **Letting a personal API key approve.** An agent holding the owner's key
  could approve on the owner's behalf. Approval stays with a portal session.
- **Reusing the before-build clarification flow.** It writes into the spec
  before coding and has no pending state, no resume and no identity.

## Risks

- **Resume on kubejob.** Reusing the worktree after the job exits is
  unverified. The plan's first step checks it, with `recover` as the
  fallback.
- **Question spam.** The cap of 3 per run and the prompt rule, measured in
  E2E.
- **Bus token exposure.** It is a sealed secret, posts are redacted, and
  the feature is off when not configured.
- **CFactory answer buttons depend on #3905 user identity.** They fall back
  to a link until it lands.
- **Hosts:** prod k3s through gitops only. No p510.

## Verification

- **AIFactory unit tests:**
  - the tool writes the file to the source dir with redaction;
  - the cap of 3;
  - the loop pauses with `needs_input`;
  - the kubejob path accepts the reason;
  - the answer route: role, choice validation, approval refused for any API
    key, accepted for a session;
  - the inbox is enqueued and the build restarted;
  - MCP tools are scoped to visible projects, and `answer_question` refuses
    approval questions;
  - the bus poster is skipped when unconfigured, posts redacted text when
    configured (mocked), and covers expiry.
- **CFactory unit tests:** the question read in Needs you, and the link
  fallback.
- **Live:** E2E P5 ends in an open question. A factual P1 variant answered
  over MCP resumes and finishes. The question also appears on the bus and
  in both portals.
