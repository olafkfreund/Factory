# Spec: routes in the task contract, and the route in the evidence trail

Code lands in olafkfreund/Factory (schema, hub, main) and olafkfreund/PFactory (dev). Artifacts live here.

## Design

1. **Hub schema** (`apis/task-contract.schema.json`, `execution`): add, next to `phase_models`, `route` (string, enum `local|cheap|balanced|frontier`) and `phase_routes` (object, keys open like `phase_models` (`spec|planning|coding|qa|qa_fixer|test_gen` by convention), every value the same enum via `additionalProperties`). The enum is the catalog `class` vocabulary of `apis/model-catalog.json`, not `execution.routing.class` (`economy|standard|premium|governed`, a scorer verdict). `contract_version` stays "2". `scripts/validate_task_contract.py` gains asserts (valid route accepted, `tier-frontier` rejected, absent fields still validate) and a hub pytest `tests/test_task_contract_routes.py` pins the schema enum to the set of `class` values in `apis/model-catalog.json` so the two cannot drift. `factory_contracts` (`shared/factory-contracts`) is generated from the completion-event and status taxonomy only and holds no task-contract model, so it is not touched; the catalog and task contract are vendored by PFactory/AIFactory, not factory_contracts.
2. **PFactory emit** (`plan/emit/cost_router.py`): `apply_cost_routing` also writes `execution.phase_routes` = the catalog `class` of each picked model (`planning`, `coding`, `qa`, `test_gen`), merged over existing keys like `phase_models`. A model missing from the catalog yields no entry. `route` is not set by the router (it is a single run-level override a human or gateway client may add).
3. **Consumer preference: deferred, with evidence (Codex review, confirmed).** Returning a class name from `get_phase_model` would not select a transport: callers infer the provider from the returned string (`agents/planner.py:103-110`, `phase_config.py:423-436`), so `balanced` falls through to the default provider, and `AIFactory/apps/model-gateway/gateway.py:102-105` forwards the request body unchanged, so no component resolves a class name to a model today. Shipping a "prefer the route" switch would send an unresolvable model name, so it is NOT built; the contract carries the route (design 1, 2) and the consumer step is a follow-up issue that needs the gateway alias resolution (the epic's `model-routes` ConfigMap) and the provider-selection change first. `phase_models` behaviour is untouched everywhere. This is a recorded deviation from the task's "consumers preferring the route".
4. **Route in the signature** (`usage.py`, `render.py`): `PlanUsage` gains `route: str = ""`. Lifetime: `add()` keeps the LATEST non-empty route (unlike `model`, first wins), because session usage accumulates across reruns and the signature must name the route of the most recent run. `usage_from_obj` reads the route from a dict key `route`, from a `headers` mapping (dict key or attribute, header `X-Model-Route`, case-insensitive), and returns a usage record when only a route is present (zero tokens) so a header-bearing response without token counts is not discarded. The caller is the planner's existing normalisation of a completion/adapter (`plan/decompose/planner.py:371-377`), so any HTTP adapter that returns its response headers (or `route`) in the object it hands back is captured with no new wiring. The gateway sets no `X-Model-Route` header today (`gateway.py:63-67`): this is the reader half, exercised by a stub; the writer half is a follow-up in AIFactory. `_run_signature` writes `model_route` = `session.usage.route` if set, else `execution.phase_routes["planning"]` from `session.contract_result` if a contract has been emitted, else null. Documentation emission can run before a contract exists (`service.py:2327` vs `2429`), so null is an accepted, tested outcome. `change_id` stays null (see 6).
5. **CLI projection** (`governance_cli.py`): `MATCH_KEYS` gains `controls`, `agent_identity`, `model_route`; the text line prints them (control characters scrubbed with the existing `_clean`; `controls` joined by comma). JSON output gains the same keys (additive). Tests: JSON projection contains the three keys with the values written by a real render; `--control` and `--tier` filters, singly and together, return exactly the matching rows and exclude schema-1 rows.
6. **Deploy-to-plan join**, smallest form: a commit trailer `Plan-Slug: <correlation_key>` (the key already in registry and signature). Reader, built now: `governance_cli --repo <git-dir>` adds `commits` (sha list) to each matched row by one `git -C <resolved absolute path> log --format='%H%x00%(trailers:key=Plan-Slug,valueonly)'` call (path resolved first, so a leading `-` cannot be read as an option), comparing the trailer value to the row's `correlation_key` exactly; it shells out to `git` read-only with an argv list, no network, no secret. A repo path that is not a git repo is a clear error (exit 2), never "no commits". Writer, NOT built: AIFactory must stamp the trailer (it already stamps `Agent-Identity`, `Autonomy-Tier`, `Originator` via `core/commit_trailers.py`, but `requirements.json` does not carry the correlation key) and factory-gitops image bumps would need to copy it; both live in other repos and change deploy flow, so they are recorded as follow-up issues. Until the writer lands the join returns empty and says so in the summary line ("0 commits carry a Plan-Slug trailer").
7. **Follow-up issues** (filed, linked in the PR): route resolution in the gateway and consumer preference for `phase_routes` (AIFactory/PFactory, needs design 3's prerequisites); gateway emits `X-Model-Route`; AIFactory stamps `Plan-Slug` and the gitops bump copies it.

## Alternatives rejected

- New `tier-*` route names: the epic forbids a new vocabulary; the class set already exists and the hub test pins it.
- A "prefer the route when a gateway URL is set" switch in `get_phase_model` now: unresolvable name, see design 3.
- Replacing `phase_models` by routes: breaks every current consumer; stage 3 is additive.
- Taking `model_route` only from the cost router: that is the plan, not what ran; the header is preferred, the router is the fallback.
- A deploy join by registry lookup of image SHA: needs a service holding SHA to slug; the trailer needs none.
- A `governance_cli trace` subcommand: the CLI is flat today; one flag is smaller.
- Re-vendoring the schema into PFactory now: the pinned `HUB_SHA` must name a commit on hub main, which does not exist until the hub PR merges; the execution object tolerates unknown keys, so PFactory emits correctly before re-vendor. The re-vendor plus HUB_SHA bump is the coordinator's step after the hub merge (owner action).

## Risks

- PFactory emits `phase_routes` before its vendored schema declares it: valid (open object), but the drift gate compares the vendored copy to the pinned hub SHA, so the re-vendor must follow the hub merge or the gate and the schema diverge silently only in documentation.
- The `X-Model-Route` name is a proposal, not an existing gateway behaviour; absent header falls back to the router route, so nothing misreports.
- `git log` on a large repo is slow; the call is opt-in via `--repo`.

## Verification
