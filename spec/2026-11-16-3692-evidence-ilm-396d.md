# Spec: Evidence ILM keeps 396 days

## Design

In factory-gitops `apps/minio/manifests/manifests.yaml` (bucket Job `ilm_apply` section):

1. `Days` 90 -> 396 in the four evidence rules. Rename IDs: `evidence-90d` -> `evidence-396d`,
   `evidence-<p|a|t>factory-90d` -> `evidence-<p|a|t>factory-396d`. `mc ilm import` replaces
   the whole document, so old IDs vanish; the only references to the IDs are in this file
   (grepped across factory-gitops and Factory: nothing else names them).
   `NoncurrentDays` on `factory-evidence` stays 30.
2. Read-back asserts day counts. The image has only `mc`, coreutils and the shell, so
   `ilm_apply` takes a second list `DAYS:COUNT`, and after the export counts occurrences of
   the literal `"Days":<n>` using bash substitution (`${got//needle/}` length difference);
   it fails unless each count matches. For `factory-artifacts`: `30:3 396:3`; `factory-evidence`: `396:1`;
   `factory-backups`: `14:1`. The count is independent of key order in the export. Together with
   the existing ID check, and since the import replaces the whole document, this proves the
   expected set of expiries. `"NoncurrentDays":N` does not match the `"Days":` needle.
3. Comments and docs naming 90 days are updated (manifest header, evidence-collector comments,
   gitops `docs/evidence-collection.md`).
4. Factory compliance docs: R-006 (current L2 x I3 stays until measured after rollout; the
   gap text and treatment change), SoA A.5.33 and A.8.10 rows, SOC 2 gap rows CC6.5 and C1.2.
   Records say "396 days in the manifest at <date>; live ILM read-back by the Job after sync".

### Storage headroom (measured read-only 2026-11-16)

- `factory/minio-data` PVC: 20Gi nominal, `local-path` (capacity is not enforced by local-path).
  The backing volume mounted at `/data` in the pod: 938G total, 138G used, 801G available (15%).
- `du` per bucket: `factory-artifacts` 3.2 GiB, `factory-backups` 6.4 MiB, `factory-evidence` 4.5 MiB
  (daily dated snapshots since 2026-07-25, ~110 days).
- Projection: evidence grows ~40 KiB/day, so 396 days is about 16 MiB plus noncurrent copies.
  `factory-artifacts` evidence-tagged objects are a subset of the 3.2 GiB; at 4.4x retention the
  worst case is under 15 GiB, against 801 GiB free. Headroom is not a constraint. Note that the
  20Gi PVC figure is nominal: if the PVC is ever moved to a size-enforcing class, 20Gi is still above the worst case.

## Alternatives rejected

- Keep IDs, change only days: the ID would lie about the retention; ILM rule IDs are the audit label.
- Per-ID day assertion by slicing the export: needs a known key order and no sed/awk/grep exist in the image; the count check is order-independent.
- 365 days: below the register's 13-month floor.
- Run a temporary Job to test `mc ilm export` format: forbidden (no live cluster writes); no local MinIO exists (removed from nixpkgs).

## Risks

- The export's exact JSON spacing was not observable offline. The existing ID check already
  relies on compact `"ID":"x"`, and the same marshaller emits `"Days":N`. If the format differs, the
  Job fails loudly after the import has already applied the rules (ILM is correct, the Job is red);
  fix is a one-line needle change. Logic is unit-checked with sample JSON in both key orders.
- Longer retention means deletion later: acceptable, storage is ample.
- Retention only extends from now: an object already expired under the 90-day rule is not brought back
  by the new rule. Measured read-only 2026-11-16: `/data/factory-evidence` holds 111 daily directories from
  2026-07-25 (114 days old) to 2026-11-16, so on-disk data older than 90 days still exists. With versioning on,
  expiry writes a delete marker and keeps the data version until the 30-day noncurrent rule reaps it, so the
  disk listing alone does not show whether markers exist. Rolling out soon limits the loss; any delete marker
  on a current version would still hide it until removed (not in scope, no live writes). The compliance records
  must not claim 13 months of history before 2027-08 (collection began 2026-07-25).
