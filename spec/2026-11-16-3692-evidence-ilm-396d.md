# Spec: Evidence ILM keeps 396 days

## Design

In factory-gitops `apps/minio/manifests/manifests.yaml` (bucket Job `ilm_apply` section):

1. `Days` 90 -> 396 in the four evidence rules. Rename IDs: `evidence-90d` -> `evidence-396d`,
   `evidence-<p|a|t>factory-90d` -> `evidence-<p|a|t>factory-396d`. `mc ilm import` replaces
   the whole document, so old IDs vanish; the only references to the IDs are in this file
   (grepped across factory-gitops and Factory: nothing else names them).
   `NoncurrentDays` on `factory-evidence` stays 30.
2. Read-back asserts the day count of each rule. The image has only `mc`, coreutils and POSIX
   `/bin/sh` (no grep, sed, awk), so `ilm_apply` becomes `ilm_apply BUCKET JSON ID=DAYS...`: it walks the
   export character by character with POSIX parameter expansion, cuts it into rule objects by brace
   depth, and for each rule checks that `"ID":"<id>"` and `"Expiration":{"Days":<n>` followed by `,` or `}`
   are in the same object. It fails if a rule has the wrong days, if an expected rule is absent, or if the
   export holds a rule that was not expected (matched count and seen count must equal the argument count).
   This is independent of key order and rejects `Days":3960`. `NoncurrentDays` never matches.
   Pairs: `factory-artifacts` `log-*-30d=30` (3) and `evidence-*-396d=396` (3); `factory-evidence`
   `evidence-396d=396`; `factory-backups` `backups-14d=14`.
3. Comments and docs naming 90 days are updated: in factory-gitops the manifest header and Job comments
   (`manifests.yaml:140,269,289-291,313-315,331-361`), `apps/evidence-collector/manifests/manifests.yaml:5,271,363`
   and `docs/evidence-collection.md`; in Factory `apis/concurrency-conventions.md:100` (the "§2" the manifest
   cites) and the live-state sentences in `docs/compliance/policies/audit-logging.md:94` and
   `data-governance.md:94,263`. Historical gap narratives (README, business-continuity-dr, plan/spec of #324) stay.
4. Factory compliance docs: R-006 (current L2 x I3 stays until measured after rollout; the
   gap text and treatment change), SoA A.5.33 and A.8.10 rows, SOC 2 gap rows CC6.5 and C1.2.
   Records say "396 days in the manifest at <date>; live ILM read-back by the Job after sync".

### Storage headroom (measured read-only 2026-11-16)

- `factory/minio-data` PVC: 20Gi nominal, `local-path` (capacity is not enforced by local-path).
  The backing volume mounted at `/data` in the pod: 938G total, 138G used, 801G available (15%).
- `du` per bucket: `factory-artifacts` 3.2 GiB, `factory-backups` 6.4 MiB, `factory-evidence` 4.5 MiB
  (daily dated snapshots since 2026-07-25, ~110 days).
- Projection (an estimate assuming steady ingestion, not a bound): evidence grows ~40 KiB/day, so 396 days is about 16 MiB plus noncurrent copies.
  `factory-artifacts` evidence-tagged objects are a subset of the 3.2 GiB; at 4.4x retention the
  worst case is under 15 GiB, against 801 GiB free. Headroom is not a constraint. Note that the
  20Gi PVC figure is nominal: if the PVC is ever moved to a size-enforcing class, 20Gi is still above the worst case.

## Alternatives rejected

- Keep IDs, change only days: the ID would lie about the retention; ILM rule IDs are the audit label.
- Counting `"Days":N` occurrences per bucket: cannot tell which rule has which days (swapped 30/396 passes) and matches `3960` (Codex review finding, confirmed by test). Replaced by per-rule brace-depth parsing.
- 365 days: below the register's 13-month floor.
- Run a temporary Job to test `mc ilm export` format: forbidden (no live cluster writes); no local MinIO exists (removed from nixpkgs).

## Risks

- The export's exact JSON spacing was not observable offline. The existing ID check already
  relies on compact `"ID":"x"`, and the same marshaller emits `"Days":N`. If the format differs, the
  Job fails loudly after the import has already applied the rules (ILM is correct, the Job is red);
  fix is a one-line needle change. Logic is unit-checked with sample JSON in both key orders, reordered rules,
  nested tag arrays, swapped days, `3960`, extra and missing rules. The real export spacing is unverified offline.
- Version scope: `NoncurrentDays:30` stays on `factory-evidence`. The 396-day floor therefore covers current
  versions of untouched evidence objects (evidence is write-once under dated prefixes); a noncurrent version
  (an overwrite or delete) is still reaped 30 days later. The compliance rows say exactly that. The
  `factory-artifacts` evidence rules have no noncurrent expiry, so versions there are not bounded by the
  retention multiplier; this already holds today and is out of scope (storage is ample).
- Longer retention means deletion later: acceptable, storage is ample.
- Existing delete markers (possibly imminent loss): the 90-day rule has run since 2026-10-22, so evidence
  dated 2026-07-25 to about 2026-08-18 (older than 90 days then) may already carry delete markers; their data
  versions would be reaped 30 days later, from about 2026-11-21. Not verifiable here (no `mc` credentials, the
  MinIO image has no `find`/`strings`). Owner action: `mc ls --versions fac/factory-evidence/2026-07-25/` and, if a
  marker exists, remove it (`mc undo`/`mc rm --version-id` on the marker) before the noncurrent reap. This is
  reported with the PR; the compliance rows do not claim history before the first surviving current object.
- Retention only extends from now: an object already expired under the 90-day rule is not brought back
  by the new rule. Measured read-only 2026-11-16: `/data/factory-evidence` holds 111 daily directories from
  2026-07-25 (114 days old) to 2026-11-16, so on-disk data older than 90 days still exists. With versioning on,
  expiry writes a delete marker and keeps the data version until the 30-day noncurrent rule reaps it, so the
  disk listing alone does not show whether markers exist. Rolling out soon limits the loss; any delete marker
  on a current version would still hide it until removed (not in scope, no live writes). The compliance records
  must not claim 13 months of history before 2027-08 (collection began 2026-07-25).
