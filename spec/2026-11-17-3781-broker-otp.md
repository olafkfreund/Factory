# Spec: Keycloak post-broker-login conditional OTP

## Design

New factory-gitops app `apps/keycloak-broker-otp` (CronJob `keycloak-broker-otp`, daily 05:40, same pinned Keycloak 26.1 image, same `KEYCLOAK_ADMIN_PASSWORD` secret reference, same hardening as `keycloak-mfa`). Mode `BROKER_OTP_MODE`, default `audit`:

| mode | writes |
|---|---|
| `audit` | nothing; logs whether the flow exists and which flow the IdP uses |
| `install` | the `post-broker-otp` flow, if absent; no login changes |
| `bind` | as install, then sets the IdP's `postBrokerLoginFlowAlias`; refuses to replace a different flow |
| `unbind` | clears the binding if it is ours; the flow stays |

The flow (declarative: `apps/keycloak-broker-otp/manifests/post-broker-otp.realm.json`, realm-export format, usable by `kc.sh import` for a rebuilt realm):

- `post-broker-otp` (top level)
  - `post-broker-otp-conditional` (CONDITIONAL, priority 10): `conditional-user-configured` (REQUIRED, 10) then `auth-otp-form` (REQUIRED, 20)
  - `allow-access-authenticator` (REQUIRED, 20)

Why these parts, found by testing in a throwaway container: explicit priorities, because equal priorities are ordered by id, not by intent; and the unconditional `allow-access-authenticator`, because a post-broker flow whose only step is a skipped conditional fails every login of a user without OTP (`invalid_user_credentials`). Partial import cannot carry flows, so the job builds the tree with `kcadm`; the e2e test diffs the live flow against the JSON, so the file cannot drift from the job.

The job reads first and writes after. An existing flow that differs from the JSON is refused by `install` and `bind`, never edited, and `audit` reports it as `flow_present=drift`; `unbind` ignores drift, because it is the way out of a broken flow. The `master` realm is never addressed. Users with an OTP credential are challenged on every brokered login; users without one pass and are enrolled by `keycloak-mfa` (`CONFIGURE_TOTP`).

Tests (dev only): `e2e-local.sh` starts a throwaway Keycloak 26.1, uses a second realm as a stand-in for GitHub (OIDC, alias `github`), drives the browser flow with curl, and runs the real scripts. A GitHub workflow runs it on PRs touching the app (not a required check: docker and a 400 MB pull). Findings recorded here: `requiredActions+=CONFIGURE_TOTP` on 26.1 appends, keeps `UPDATE_PASSWORD`, and adds no duplicate on a second run; a brokered login with `CONFIGURE_TOTP` pending is sent to the OTP enrolment form, with the flow unbound and bound (the test fails otherwise).

Docs: `docs/keycloak-sso.md` "MFA" gains the new job, the owner checklist (master console login, break-glass account, then `bind`), rollback (`unbind`), and the corrected "known limits".

## Alternatives rejected

- Required OTP form in the post-broker flow (no condition): forces enrolment inside the login and would interfere with the `keycloak-mfa` ladder; the conditional form leaves enrolment to the job.
- Editing the built-in `first broker login` flow: mixes first-login logic with per-login MFA and hides the change in a built-in.
- Realm import at Keycloak start (`--import-realm`): skips an existing realm, and the live realm is never re-imported.
- A Terraform/operator-managed realm: a new tool for one flow.
- A Kyverno-style guard on the IdP: Keycloak state is not a Kubernetes object.

## Risks

- A user with an OTP credential who lost the authenticator is locked out of brokered login until the `master` admin resets the credential (recorded in the docs). Mitigation: `audit` then `install` then `bind`, one PR each, plus the owner's break-glass checklist.
- Real GitHub brokering differs from the stand-in IdP: the owner's throwaway-account login is the final test.
- `kcadm` output formats change between Keycloak versions: the pinned image digest and the `audit` run catch it before any write.

## Verification

`bash apps/keycloak-broker-otp/manifests/e2e-local.sh` passes: baseline unchallenged; install idempotent and not bound; realm JSON equals the live flow; bound: no-OTP user passes, OTP user challenged, wrong code refused, right code accepted; unbind restores plain login; `requiredActions+=`; pending `CONFIGURE_TOTP`; a hand-edited flow is refused by install/bind, shown by audit, and unbind still works. `kustomize build` succeeds. The owner's live brokered test stays open under #3781.
