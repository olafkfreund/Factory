# Spec: move the api_get call sites to protocol methods (RFC-0022 Phase 2b)

## Design

### Audit (identical in AIFactory, PFactory, TFactory at origin/dev, 2026-11-17)

| # | Site | What it reads | Replacement |
| - | ---- | ------------- | ----------- |
| 1 | `routes/github.py` `_get_provider_issue_comments`, GitLab issue notes | issue comments | `fetch_comments` |
| 2 | same, GitLab merge-request notes fallback | PR comments | `fetch_pr_comments` (new) |
| 3 | same, Azure DevOps work-item comments | issue comments | `fetch_comments` |
| 4 | same, Azure DevOps PR threads fallback | PR comments | `fetch_pr_comments` (new) |
| 5 | same, GitHub `repos/{repo}/issues/{n}/comments` | issue/PR comments | `fetch_comments` |
| 6 | `services/delegation_runner.py` `_existing_enrichment_comment` | issue comments, scans for a marker | `fetch_comments` |

Sites 1-5 are one function, which is called from two routes (single issue view and the bulk view). Site 6 is a dedupe check.

**Integer issue number dependence (input to Factory#3774).** No site does arithmetic, ordering or dictionary-key work on the number. The route parameter is declared `issueNumber: int` (FastAPI coerces and rejects non-numeric input), the value is interpolated into URL strings, and `_existing_enrichment_comment(provider, issue_number: int)` passes it through. The protocol methods they move to take `int` (`fetch_comments(issue_number: int)`; `fanout_comments` calls `int(number)`), so the real int dependencies after this change are the hub protocol signatures and the route parameter, not the call sites. Two provider-specific leftovers matter for Phase 1: the GitLab/ADO PR fallbacks key on the same number as the issue (GitLab IID versus MR IID, ADO work item id versus PR id are different namespaces that happen to share a numeric type), and the response `id` of a comment is an int today but `IssueComment.id` is a `str`.

### Hub change (additive)

1. `IssueComment` gains `avatar_url: str = ""` as its last field. The board response shows the author avatar; without the field the route would have to read `raw_data` per provider, which is the provider branching this phase removes. GitHub fills it from `user.avatar_url`, GitLab from `author.avatar_url`, Azure DevOps from `createdBy._links.avatar.href`.
2. `CodeProvider.fetch_pr_comments(pr_number, since=None) -> list[IssueComment]`: a pull request's discussion comments, oldest first, raising `ProviderCommentError` rather than returning a partial thread. GitHub delegates to `fetch_comments` (a PR's conversation lives on the issues endpoint). GitLab reads `merge_requests/{n}/notes` through the same walk as issue notes (shared helper, system notes dropped). Azure DevOps reads `pullRequests/{n}/threads`, skips deleted threads and comments, and applies `since` client-side (the endpoint has no cursor). `HttpGitHubProvider` raises the existing "VCS half" `NotImplementedError`.
3. `shared/factory-github/providers/__init__.py` needs no change.

### Service change (per service, one PR each, base dev)

- Re-vendor the canonical files from the hub commit that carries (1) and (2), and bump `HUB_SHA` in `factory-github-drift.yml` to it. CFactory does the same re-vendor and bump without a caller change, so the four copies agree.
- Rewrite `_get_provider_issue_comments` to: try `fetch_comments(n)`; on failure try `fetch_pr_comments(n)`; on a second failure log and return `[]` (the present behaviour). Map each `IssueComment` to the existing response dict (`id` as int when numeric, `body`, `user.login`, `user.avatar_url`, `created_at`, `updated_at` as ISO strings). No `provider_type` branching remains.
- `_existing_enrichment_comment` uses `fetch_comments` and returns `int(c.id)` of the first comment containing the marker.
- Update the service's own test double (`runners/github/testing.py`) and the existing tests that stub `api_get` for these paths.

## Alternatives rejected

- **Drop the two PR fallbacks.** Silently loses PR comments the board shows on GitLab and Azure DevOps today.
- **Read `raw_data` in the route for avatars.** Keeps provider-shaped parsing in three services.
- **Add `fetch_pr_comments` to `WorkItemProvider`.** Jira has no pull requests; the method is VCS.
- **Make `fetch_comments` accept a PR flag.** Changes a signature four vendored copies and the bulk path rely on.
- **Leave the PR sites on `api_get` and carve them out of Factory#3772.** Defeats the removal.

## Risks

- Hub protocol change reaches all four vendored copies; the drift gates catch a missed file, and the pin must be on hub main, so the hub PR merges first.
- GitLab comment order changes from API order (newest first) to oldest first, as the protocol promises. The board sorts by `created_at`; verified in the service tests.
- A GitHub failure now makes a second identical call via `fetch_pr_comments`. Bounded (one extra call on an error path).
- GitHub previously returned one page (30); `fetch_comments` pages to completion, so a very long thread costs more calls, correctly.

## Verification

- Hub: unit tests per provider for `fetch_pr_comments` and `avatar_url`; protocol conformance test lists the new member; the hub test suite and ruff/mypy pass.
- Services: tests for the rewritten function (issue path, PR fallback, double failure) and the delegation dedupe; `grep api_get` over non-test, non-provider code returns nothing; drift gate green on the exact head SHA.
