# Spec: treat a never-seen field as zero matches, visibly

## Design

In `evaluate()` (factory-gitops `apps/security-alerts/manifests/alerts.py`), on `HTTPError` 400 read
the response body (never printed), parse it as JSON once and, only if `code` is 20004 and `message` says
`No field named action` (the rule's own field), return `("no_field", None)`. Malformed, unreadable or any
other body stays `error`. `no_field` is not an error: `main()` leaves rc at 0. It
is written to `job_health` with `count` null and is never `ok`, so the state is queryable and distinct
from a healthy zero. It means detection is unavailable, not that zero failures were proven. Every other 400, 5xx and transport error remains `error` (rc 1). The window
and `audit_chain` stream are unchanged. `not_configured` stays rc 0 (tested).

## Alternatives rejected

- Query `kind` instead of `action`: the chain forwarded today has no auth-failure `kind`, and the
  rule is defined on AIFactory's `auth.failure` action; guessing a value would be silent and wrong.
- Treat every 400 as zero: hides real query bugs, the opposite of the loud-failure requirement.
- Fail the Job on `no_field`: the Job could not succeed until an auth failure is first ingested, so
  job-watchdog would stay critical indefinitely. Codex asked for an explicit decision: the owner's
  advance approval of this round accepts degraded (visible, exit 0) monitoring until the first row
  arrives; whether `audit_chain` ever receives AIFactory `auth.failure` is a follow-up for the owner.
- Seed a fake `auth.failure` row: writes fabricated audit data.

## Risks

If auth failures never reach `audit_chain`, the Job stays green while the rule cannot detect them; `no_field`
in `job_health` is the only signal. A mis-spelled field no longer fails the Job; the match is limited to the
rule's own field `action`, and a test pins the SQL text.
