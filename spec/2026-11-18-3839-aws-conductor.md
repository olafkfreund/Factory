# Spec: fail-closed AWS conductor, pre-flight, template fixes

## Design

**Canonical location.** `.claude/skills/run-aws-demo/{SKILL.md,conductor.sh}`
in the hub (the hub already versions `.claude/skills/`). The
`~/.claude/skills/run-aws-demo/` copy is overwritten from it. The test lives at
`tests/test_run_aws_demo_conductor.py` (pytest is the hub's runner; no bats is
installed) and drives the script with a stubbed `terraform`, `aws`, `docker`,
`curl` and `python3` on `PATH`.

**Conductor changes (`conductor.sh`).**
- `set -euo pipefail`, plus `fail()` that prints `FAILED at <step>: <quoted
  AWS error>` to stderr and exits 1.
- A `run_tf <step> <logfile> args...` helper: `terraform ... > log 2>&1`, on
  non-zero exit prints the last 15 lines of the log and fails. No pipe to
  `tail` for apply/destroy; the tail is shown only after the status is known.
- Classify the log: `can't create new App Runner services` yields the precise
  owner message (open an AWS support case to enable App Runner service
  creation for the account, or use another account; see
  `docs/aws-app-runner-restriction.md`).
- Pre-flight (step 0b, before scaffold/build): `aws apprunner list-services
  --max-items 1`. A failure stops early with its error. It proves identity,
  region and App Runner API access, not creation eligibility.
- After apply: URL outputs must be non-empty `https://` strings, else fail.
- Step 7: pytest status is captured (`PIPESTATUS`-free: output to a log, then
  `tail`); only exit 0 reaches the "GREEN" line. Any failure exits non-zero.
- Teardown trap stays on EXIT and preserves the original exit status
  (`rc=$?` at the top, `exit $rc` at the end); destroy failures are reported
  but do not mask the primary failure.

**Docs.** New `docs/aws-app-runner-restriction.md` (symptom, request ids,
owner step, alternatives); SKILL.md gains a "Known blocker" section and the
fail-closed behaviour.

**Template (`templates/cloud-deploy/aws/main.tf`).** Add: default VPC lookup
with subnets, a security group for the connector (egress) and one for the data
stores (ingress 5432/6379 from the connector SG), `aws_apprunner_vpc_connector`
wired into `network_configuration.egress_configuration`; an
`aws_iam_role` for `build.apprunner.amazonaws.com` with
`AWSAppRunnerServicePolicyForECRAccess` and `authentication_configuration.access_role_arn`;
`db_subnet_group_name`/`vpc_security_group_ids` on RDS and
`security_group_ids` on ElastiCache; names `factory-ttt-*`; provider
`default_tags` `factory-ephemeral=true`, `managed-by=factory`. Port `8080`
and variables unchanged. If the VPC wiring does not validate cleanly, the
network part is dropped and recorded as follow-up (no guessing).

## Alternatives rejected

- ECS Fargate / Lightsail target: a design decision, out of scope. Recorded as
  the recommended follow-up (it avoids the App Runner account gate).
- bats: not installed in the hub toolchain; pytest + stubs gives the same proof.
- A canary `CreateService` as pre-flight: creates a real billable resource,
  owner-gated.
- Keeping the skill only in `~/.claude`: untested and unversioned.

## Risks

- Real AWS behaviour is untestable offline: the stubs only prove control flow.
  Mitigation: the owner runs the conductor once after the account step.
- Template networking may be incomplete at runtime (validate checks structure
  only); noted in the doc.
- `set -e` interacts with the existing `getval`/grep pipelines; each
  expected-failure command is guarded.
