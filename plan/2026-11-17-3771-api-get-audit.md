# Plan: move the api_get call sites to protocol methods (Factory#3771)

Self-contained summary of the approved decisions (spec `spec/2026-11-17-3771-api-get-audit.md`):

- Six `provider.api_get` sites per service (AIFactory, PFactory, TFactory, origin/dev): five inside `_get_provider_issue_comments` in `apps/web-server/server/routes/github.py`, one in `_existing_enrichment_comment` in `apps/web-server/server/services/delegation_runner.py`. Three route sites and the delegation site read issue comments (`fetch_comments`); two route sites (GitLab MR notes, ADO PR threads) read PR comments, which need a new hub method `CodeProvider.fetch_pr_comments(pr_number, since=None) -> list[IssueComment]`.
- `IssueComment` gains `avatar_url: str = ""` (last field).
- Hub change is additive. Services re-vendor the canonical files and bump `HUB_SHA` to a hub-main commit that carries it; CFactory re-vendors too (no caller change).
- Concrete providers and `GHClient` keep `api_get`/`api_post`; this issue removes nothing.

### Audit finding for Factory#3774 (record on #392)

No call site does arithmetic, ordering or key work on the issue number. It is a FastAPI `issueNumber: int` route parameter, interpolated into URLs, passed to `fetch_comments(issue_number: int)` (and `fanout_comments` calls `int(number)`). `IssueComment.issue_number` is `int` and `IssueComment.id` is `str` while the board response `id` is an int today. The GitLab/ADO PR fallbacks reuse the issue number for a different namespace (MR IID / PR id). Phase 1 therefore needs: the route parameter type, the protocol signatures, and the response `id` coercion; the call sites themselves are indifferent.
