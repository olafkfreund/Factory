# Plan: factory coders can ask the user mid-build (#3906)

## Approved decisions

Everything the spec decided, so this plan can be followed without it.

### The question and the pause

- **The tool.** `ask_human` is available to the **Claude coder session
  only**. It is registered in the coder client's tool list, never in
  `create_all_tools`, so the standalone MCP server never exposes it.
  - **Arguments:** `question`, `choices` (2-6, optional), `needs_approval`,
    `context`, `default` (a suggestion only, never applied),
    `timeout_minutes` (default 30, at most 1440).
  - **Budget:** 3 questions per run, 10 per task.
- **The question file** is `questions/<qid>.json` in the worktree spec dir,
  with `status: "open"`, `asked_at`, `asked_by_model` and `run_id`. The tool
  answers "Question recorded. Stop now…".
- **The pause is owned by the runner,** in the coder's turn loop after
  `run_session_guarded`. In order:
  1. commit the work in progress to `aifactory/<spec>` as
     `wip: paused for question <qid>`, and push it;
  2. move `questions/` to the source spec dir (local) or upload it with
     `push_questions` (packed);
  3. write `review_state.json` with `reason: "needs_input"`, and set the
     plan to `human_review` with `reviewReason: "needs_input"`;
  4. return. No recovery, QA, finalization or auto-continue runs.
- **The control plane confirms the pause.**
  - Locally, `process_monitor` gains a `needs_input` branch.
  - On kubejob, `_pause_confirmed` accepts the pause only when
    `fetch_questions` returns an open question for this run. Otherwise the
    run counts as a normal completion.
  - The reason survives `write_control` and `_update_plan_status`.
- **The coder prompt** says when to ask:
  - **Ask when:** the requirement is ambiguous or contradictory; the change
    is outside the plan's files; or the change is destructive.
  - **Never ask:** about something the plan or the repository already
    answers.

### Answers and resuming

- **The record.** The control-plane question file is the single record. It
  moves from `open` or `expired` to `answered` once, under a file lock; a
  second answer gets 409.
- **Routes:**
  - `GET /api/tasks/{id}/questions`;
  - `POST /api/tasks/{id}/questions/{qid}/answer` (`answer`, or
    `decision` plus `note`);
  - `GET /questions/{qid}/confirm-token`.

  A `qid` must belong to its task, and the answer must be one of the
  choices.
- **Who can answer:**
  - **Any question:** project role member or higher.
  - **Approval questions** also need all of these:
    - a JWT principal with no `api_key_id`, `scoped_service`,
      `is_legacy_shared_token` or `is_service`;
    - a JWT sent as a **cookie**, not a bearer header;
    - a one-time `confirm_token`, valid for 5 minutes and bound to the user,
      the question and the session.

    Anything else gets 403. The audit fields (`answered_by`, `channel`,
    `auth`, `answered_at`) come from the request context, not the body.
- **A rejected approval** sets the question to `rejected` and
  `reviewReason: "approval_rejected"`. There is no resume. Start and
  recover return 409 while an approval question is open or rejected.
- **Delivery.**
  - The answer goes into the **source** spec dir's `inbox/agent.json`, with
    its `qid` and `answer_id`.
  - Its delivery state goes `pending` → `launched`, through the existing
    start path. A failed launch stays `pending` and the checker retries it.
  - Draining marks the message read in both copies, keyed by `answer_id`.
- **Resuming.** Locally, in the same worktree. On kubejob, the dispatcher
  clones and checks out `aifactory/<spec>` instead of the base tip.

### Around the edges

- **MCP:**
  - `aifactory.questions_pending` (`mcp:read`) needs no `task_id`, filters
    to the projects the key's user can see, and lists open and expired
    questions.
  - `aifactory.answer_question` (`mcp:write`) needs `task_id` and `qid`. It
    refuses ownerless and legacy keys, and refuses approval questions,
    returning the portal link instead.
  - Both tools exist in remote MCP and in mcp-stdio.
- **The bus notice** is fixed text: `[factory] a question is waiting for
  you — run aifactory.questions_pending or open <portal>/needs-input`.
  - It never contains question text, names or answers.
  - The bot token lives in the control plane, as a sealed secret, and is
    sent only to the configured HTTPS homeserver.
  - With no configuration, nothing is posted.
- **The checker** runs every 60 s in the web-server lifespan, separate from
  the merger. It:
  - expires overdue questions (they stay answerable);
  - posts a notice for each expiry;
  - retries pending launches.
- **Merger guard.** The merger (`_process_spec`, `_sync_status`) and
  `routes/pr.py` skip any task whose `reviewReason` is `needs_input`,
  `approval_rejected` or `plan_review`.
- **Portals.**
  - **AIFactory:** a Needs input banner with answer or approve controls; the
    board shows "Needs input"; merge-review actions are hidden.
  - **CFactory:** carries `reviewReason` and the question summary; disables
    `approve_review` and `reject_review` for these reasons; shows the
    question with a link to AIFactory.
- **E2E:**
  - P5 must end in an open question that survives a merger tick, with no PR,
    no TFactory hand-off, and the WIP commit on the task branch.
  - A factual P1 variant answered over MCP must resume and finish.
  - The harness never answers approval questions.
- **Out of scope:** non-Claude coding providers, and answer buttons inside
  CFactory (they wait for #3905's user identity).
- **Deployment:** prod k3s through gitops only. No p510.

## Steps

1. **The question store and the `ask_human` tool.**
   - Add `apps/backend/agents/questions.py`:
     - `write_question`, `read_question`, `list_questions`,
       `update_question` (compare-and-set under flock);
     - budget counters per run and per task.
   - Add `ask_human` in `apps/backend/agents/tools_pkg/tools/human.py`.
     Register it only in the coder client's tool list (`core/client.py`
     ~950). Leave `registry.create_all_tools` and the standalone MCP server
     alone.
   - Add the "when to ask" rule to the coder prompt (`prompts/coder*.md`).
   - **Tests:** `tests/test_questions_store.py`, `tests/test_ask_human_tool.py`
     (new):
     - the file is written to the worktree spec dir;
     - both budgets are enforced;
     - choices are validated;
     - `ask_human` is absent from `create_all_tools` and from the standalone
       MCP server.
   - **Verify:** `<backend pytest> tests/test_questions_store.py
     tests/test_ask_human_tool.py -q`

2. **The pause, owned by the runner.**
   - In `agents/coder.py`'s turn loop (~880-1018), right after
     `run_session_guarded`, when an open question from this run exists:
     1. make the WIP commit and push it, with the same mechanism as the
        packed push (`workspace_fetch.py` ~106-185);
     2. move the questions: copy `questions/` to the source spec dir
        (local), or call `push_questions` (new, keyed per run, in
        `workspace_fetch.py`) and pair it with `fetch_questions`;
     3. write `review_state.json` with `needs_input` and the `qid`, and set
        the plan to `human_review` / `needs_input`, synced to the source;
     4. return.
   - In `cli/build_commands.py` (~612), skip QA while a `needs_input` pause
     is in place.
   - **Tests:** `tests/test_ask_human_pause.py` (new):
     - the WIP commit is made;
     - local copy and packed push both work;
     - `review_state` is written;
     - no QA, no recovery and no auto-continue run.
   - **Verify:** `<backend pytest> tests/test_ask_human_pause.py
     tests/test_solo_mode.py tests/test_workspace_fetch_plan.py -q`

3. **The control plane confirms the pause.**
   - `services/process_monitor.py` (~418-499, 777-794): add a `needs_input`
     branch. It must not auto-continue or complete. It emits
     `human_review/needs_input` and releases the slot.
   - `services/agent_kubejob.py` (~76-150, 336-374):
     - add `needs_input` to `_REVIEW_PAUSE_REASONS`;
     - `_pause_confirmed` calls `fetch_questions` and requires an open
       question for this run;
     - without one, it runs the normal completion path.
   - `task_control.write_control` and `_update_plan_status` keep the
     `needs_input` reason.
   - **Tests:**
     - local: the pause is emitted and no completion or TFactory hand-off
       happens;
     - kubejob: the pause is accepted with an open question and refused
       without one (falling back to completion).
   - **Verify:** `<backend pytest>` with the new
     `tests/test_needs_input_confirm.py`, plus the existing
     `tests/test_build_backend_kubejob.py`.

4. **The answer API, approval identity, delivery and resume.**
   - Add `routes/questions.py` (registered in the app) with GET list, POST
     answer and GET confirm-token, applying the rules above.
   - The approval check is a dependency, `require_interactive_session`, that
     reads `request.state.user`, how the JWT arrived (cookie or bearer), and
     the `confirm_token` (HMAC with the app secret, plus a single-use record).
   - **Delivery:**
     - write into the source spec dir's inbox (through `inbox_service`,
       pointed at the source dir);
     - start the build through the existing start service, and record the
       delivery state;
     - add 409 guards on `routes/execution.py` start and recover while an
       approval question is open or rejected.
   - **`agents/inbox.py`:** draining marks a message read in the source copy
     too, keyed by `answer_id`.
   - **Kubejob resume:** the dispatcher (`build_backend.py` ~1428-1472)
     checks out `aifactory/<spec>` when the task has a `needs_input` WIP
     checkpoint.
   - **Tests** (`tests/test_questions_api.py`, new, plus the existing ones):
     - **Answers:** a second answer gets 409; an answer races expiry; a
       `qid` from another task is refused; a non-choice answer is refused.
     - **Approval:** refused for an `acw_` key, a scoped key, the legacy
       token and a bearer JWT; accepted for a cookie session plus
       `confirm_token`; a reused token is refused.
     - **Rejection:** rejecting keeps the task stopped.
     - **Guards:** start and recover get 409.
     - **Delivery:** a launch failure stays `pending`; no replay after a
       restart.
     - **Resume:** the kubejob checkout of the WIP branch.
   - **Verify:** `<backend pytest> tests/test_questions_api.py
     tests/test_build_backend_kubejob.py -q`, plus the web-server tests the
     change touches.

5. **The question checker, and the merger and PR guards.**
   - Add `services/question_checker.py`, started in the web-server lifespan
     (every 60 s):
     - expire overdue questions;
     - post one notice per expiry through step 6's notifier (call it only if
       it exists; otherwise leave a TODO hook that step 6 fills in);

   - `services/merger.py` `_process_spec` and `_sync_status`, and

     - a merger tick on a paused branch with commits opens no PR and

     - the manual PR route returns 409 on a paused task.
   - **Verify:** `<backend pytest>` with the new
     `tests/test_question_checker.py` plus the existing

## Tests

Every step's Verify command must pass, and so must the full AIFactory backend
and web-server suites and the CFactory suite.

## Rollback

- **AIFactory:** revert the PR on `dev` and cut a patch release. A paused
  task stays `human_review/needs_input`, and can be archived or retried
  manually.
- **CFactory:** revert its PR, which brings back the generic actions.
- **Bus:** remove the bus config to stop notices.
