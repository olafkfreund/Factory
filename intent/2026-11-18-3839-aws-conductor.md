# Intent: AWS demo conductor fails closed, App Runner pre-flight, template fixes

## Problem

Level 10 of the 2026-11-18 campaign (account 533267307120, eu-west-2) found
three faults on the AWS path:

1. `terraform apply` of App Runner fails with `InvalidRequestException:
   Account 533267307120 can't create new App Runner services` (CreateService,
   400; request ids 12b71da4-65d4-49f3-adda-4e608c2495dd and
   f8bad538-28d9-478f-bb25-ff6803d8d753). This is an account-level
   restriction. Only the owner can lift it (AWS support case).
2. The `run-aws-demo` conductor hides the failure two ways. The apply is piped
   through `tail -1` (truncating the AWS error), and the script has `pipefail`
   but no `errexit` and no explicit check around apply, the output lookups or
   pytest. Output lookups return empty URLs, pytest fails 5/5, and the script
   still prints "AC verification all GREEN" and exits 0.
3. `templates/cloud-deploy/aws/main.tf` claims a VPC connector it does not
   have, uses a private ECR image without `access_role_arn`, and has no
   `factory-*` names or `factory-ephemeral` tag, so the sweeper misses it.

## Proposed outcome

- The conductor stops on any failed step, quotes the AWS error, exits non-zero
  and never prints "GREEN" unless the AC tests passed against non-empty URLs.
  A shell test with a stubbed terraform proves it.
- A cheap read-only pre-flight runs before any build (it proves AWS
  identity and App Runner API access, not creation eligibility: no
  non-creating eligibility check is known). The restriction error from the
  apply is recognised and explained with the likely owner step.
- The owner step (open an AWS support case asking to enable App Runner
  service creation; unverified that support can grant it, so the doc also
  lists another account or the follow-up compute target) is documented in the skill and a hub doc.
- The template is tagged, named `factory-*`, authenticates to ECR and has a
  real VPC connector with subnets and security-group rules for RDS and
  ElastiCache, and `terraform validate` passes. Validation checks structure
  only; runtime connectivity stays unproven until App Runner is allowed.

## Affected users and systems

Anyone running `/run-aws-demo`; the hub template `templates/cloud-deploy/aws`;
AIFactory deploy templates (unchanged here). The conductor is a plain file in
`~/.claude/skills/run-aws-demo/`, not versioned anywhere today; this change
makes the hub copy the canonical, versioned source.

## Constraints

- No `terraform apply`, no AWS resource creation, no real AWS call from this
  work. Offline only (`terraform validate`, stubbed tests).
- No change of compute target (ECS Fargate / Lightsail): a design decision,
  recorded as the recommended follow-up.
- The AWS support case is owner-only.

## Open questions

None. Decision (owner delegation 2026-11-18): the hub copy under
`.claude/skills/run-aws-demo/` is canonical; the `~/.claude` copy is
synchronised from it. Reason: the hub already versions `.claude/skills/`, and
a tested script must live under version control.
