# Intent: finished builds reach a human as a pull request

## Problem

The fleet produces working branches and then stops. Nothing turns a finished
build into a pull request, so the work never reaches the person who has to
review it.

Measured 2026-09-18: **19 AIFactory tasks sit in `human_review`, all in one
project, and none has a PR.** The issue was filed at eight. The number only goes
up, because nothing drains it.

Three things combine to cause this:

1. **Landing has no owner.** AIFactory's `pr_endgame`
   (`apps/web-server/server/services/pr_endgame.py`) can push, open a PR and
   request review, but it runs only as a side effect of one build finishing
   clean. It has no queue, so it cannot pick up a branch that is already
   parked, and nothing retries it. PFactory and TFactory have no landing
   machinery at all. CFactory advertises `auto_pr` as a capability but no
   component acts on it.
2. **Being honest ends the loop.** When the QA agent's sandbox lacks the
   toolchain (e.g. no `java`/`gradle` for a Kotlin build), the QA agent cannot
   run the gate itself. It correctly refuses to record a pass it did not
   observe (AIFactory#1496). The build then stays unapproved forever, even when
   a trailing gate elsewhere already ran it. Relatedly, a trivial commit after
   the gate invalidates the gate's evidence (AIFactory#1546 binds evidence to the tree),
   and nothing re-runs the gate.
3. **One state means two things.** `human_review` means both "plan waiting
   for approval" and "build finished, waiting to land". An operator cannot
   tell parked work from pending work. Two of the 19 tasks share a title
   (010/011), and nothing shows which one is real.

## Proposed outcome

- Every build whose gates passed becomes an open PR without anyone acting,
  including the 19 already parked, and none is silently dropped.
- A build whose gate could not run in the QA sandbox, but did run in the
  trusted gate Job against the final tree, reaches a PR. It does not park.
- An operator can see at a glance which tasks await plan approval and which
  await landing.
- Merging stays a human decision. The goal is a PR on a human's desk.

## Affected users and systems

- AIFactory: `pr_endgame`, `merge/merge_policy.py`, the `human_review`
  status and every route or UI that filters on it, and the QA
  `update_qa_status` gate.
- CFactory: the cockpit is the only component that sees every service. It
  currently advertises `auto_pr` with nothing behind it.
- Hub: a candidate home for a shared module, vendored the same way as
  `job_dispatch`.
- Operators who review PRs; the one project currently holding the 19 parked
  tasks.

## Constraints

- **No auto-merge.** `AIFACTORY_AUTO_MERGE` stays off. The gates only became
  trustworthy recently.
- **The QA agent must never record a pass it did not observe.** AIFactory#1496
  stays enforced. The fix hands the QA agent real evidence; it must not weaken
  the refusal.
- Gate evidence must match the tree that gets merged. Evidence from an earlier
  commit does not count.
- Only one copy of the logic (per "one engine, no drift"). If more than one
  service needs it, it lives in the hub, and each service's vendored copy is
  guarded by a drift gate.
- Pushing a branch and opening a PR need GitHub credentials. These go through
  env or the credential helper, never argv.
- GitHub only for now. CFactory reports GitLab/ADO `auto_pr` as NONE and that
  stays true.

## Open questions

1. **Scope.** The issue proposes four things. Which are in this task?
   Proposed: (1) the merger queue, (2) splitting `human_review`, and (4)
   letting QA use trusted gate evidence. Proposed out of scope: (3) separating
   integration from release in AIFactory, which is a CI/release-pipeline change
   and gets its own issue.
2. **Where the queue lives.** Proposed: in AIFactory, next to `pr_endgame`,
   because only AIFactory produces branches today. It would become a shared hub
   module only when a second service needs it. The issue leans towards a hub
   module driven by CFactory; that is more design for a single producer.
3. **The 19 parked tasks.** Should the new queue open PRs for them
   automatically, or should they first get a one-off review? Two are
   duplicates, and some may predate the gate fixes.
4. **Name for the new state.** Suggested: `plan_review` for "plan awaiting
   approval" and `awaiting_merge` for "PR open, waiting for a human". The
   choice affects every consumer that filters on `human_review`.
