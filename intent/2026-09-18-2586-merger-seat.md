# Intent: finished builds reach a human as a pull request

Revision 2. Revision 1 was approved on a wrong measurement: it counted 19
tasks in `human_review` and assumed none had a PR, without checking. The
facts below were measured on 2026-09-18 against the live AIFactory pod and
the target repo.

## Problem

AIFactory already has a component whose job is to open PRs: the merger
(`apps/web-server/server/services/merger.py`, AIFactory#1552/#1555, deployed
on `main`). It is an idempotent sweep that opens a PR for each pushed branch
with real commits and no open PR, and it never merges. The loop still does
not close, for three reasons:

1. **Nothing runs the merger.** Its only trigger is a manual
   `POST /api/maintenance/merger/run`. No schedule calls it, and no build
   completion calls it either.
2. **The merger drops real work.** It measures `origin/<branch>` against
   `origin/<base>`. It never checks the worktree. Five tasks
   (002, 007, 008, 009, 010) hold 2 to 10 commits that were never pushed.
   The merger reports them as `no_content (ahead_by=0)` and skips them. This
   breaks the merger's own "never drop work" rule, and its report hides it.
3. **Task status never follows the PR.** The 19 tasks in `human_review`
   (project `888c19de…`, repo `olafkfreund/pfactory-friends-demo`) are in
   five different real states:

   | Tasks | Real state |
   |---|---|
   | 001, 004, 005, 006 | PR merged 2026-09-08 |
   | 003 | PR closed without merging |
   | 011–018 | PR open, unreviewed for 7 days |
   | 002, 007–010 | unpushed commits, no PR |
   | 019 | no commits at all |

   One status covers all five states, and it also means "plan awaiting
   approval". An operator cannot tell done work, rejected work, work waiting
   on them and lost work apart.

## Proposed outcome

- The merger runs without anyone having to trigger it.
- A task whose worktree has commits that were never pushed gets them pushed
  and a PR opened. It is never reported as `no_content`.
- Each task's status reflects its PR: open (`awaiting_merge`), merged (done),
  closed without merging (rejected), or no work produced. `plan_review`
  replaces `human_review` for plans awaiting approval.
- The 19 tasks listed above end up in the status that matches their PR state.
- Merging stays a human decision.

## Affected users and systems

- AIFactory: `services/merger.py`, `routes/merger.py`, `pr_endgame.create_pr`,
  the `human_review` status and every route or UI that filters on it
  (`routes/task_service.py`, `services/process_monitor.py`,
  `services/agent_service.py`, `routes/execution.py`, frontend task types).
- The `pfactory-friends-demo` project and its 19 tasks.
- Operators who review PRs.

## Constraints

- **No auto-merge.** `AIFACTORY_AUTO_MERGE` stays off.
- The QA agent never records a pass it did not observe (AIFactory#1496).
  Nothing here weakens that rule.
- Pushing needs GitHub credentials, supplied via env or the credential
  helper, never argv.
- GitHub only. Non-GitHub providers stay a recorded skip.
- The merger's "never drop work" rule holds: any branch it cannot measure is
  reported as unmeasurable, never as empty.

## Decisions carried from revision 1 (still valid)

- The work lives in AIFactory, next to the existing merger. No hub module.
- State names: `plan_review` and `awaiting_merge`.
- Integration vs release is split out as AIFactory#1559.
- Existing parked tasks are handled automatically, through the same checks
  as any other task.

## Open questions

1. **Drop proposal (4), QA consuming trusted gate evidence, from this task?**
   The merger already opens a PR without QA approval, and states the
   verification status honestly in the PR body. So the QA dead-end no longer
   blocks landing; it only affects the sign-off label. Proposed: move it to
   its own issue.
2. **How the merger is triggered.** Proposed: call it at the end of every
   build, and also run a periodic sweep as a backstop (Kubernetes CronJob
   calling the existing route). The alternative is the periodic sweep only.
