# Intent: one `factory` CLI and MCP front door for Claude, Codex and agy

## Problem

Handing work from a coding agent to the factories takes four clients, four
tokens and some curl:

- PFactory, AIFactory and TFactory each ship their own stdio MCP server
  (`*/apps/backend/mcp_server/`), CFactory an HTTP one. Each reads its own
  token file (`~/.pfactory/.token`, `~/.aifactory/.token`,
  `~/.tfactory/.token`) and its own `*_API_URL`.
- The launch scripts point into each product's clone
  (`~/.codex/config.toml:225-262`), so a machine without four clones cannot
  use them, and agy has no entries at all.
- The key handover step is not reachable from MCP: PFactory MCP stops at
  `plan_approve`; the emit that signs the Task Contract and posts it to
  AIFactory is REST only (W0 added `plan_emit` for trusted sessions, but
  "submit my approved plan" is still several calls across two portals).
- Submitting our own approved `intent/`, `spec/` and `plan/` loses them:
  PFactory re-decomposes the plan, and the contract carries no record of the
  source artifacts or who approved them.
- "Where is my work" means asking three portals with three project-id
  schemes.

#3857 phase 2 (project-role enforcement, P3) is now live on all four portals
(CFactory, AIFactory 3.21.0, PFactory 0.9.1, TFactory 0.14.0), so the
precondition the parent plan set for a single login is met.

## Proposed outcome

From a clean Claude Code, Codex or agy session on any machine with the
`factory` tool installed:

1. `factory submit plan/<slug>.md` (or the slug's three files) sends an
   approved plan through PFactory to AIFactory on the trusted-plan fast path,
   without re-planning; the contract names the source artifacts (path +
   digest) and the approval record.
2. `factory test --repo R --branch B [--pr N]` starts a TFactory run against
   the cluster.
3. `factory status <id>` shows the state of a submission across
   PFactory → AIFactory → TFactory in one answer.
4. `factory mcp` exposes the same verbs as MCP tools;
   `factory mcp-config claude|codex|agy` prints (or merges) the config entry
   for each agent, keeping existing per-portal entries rather than
   replacing them.
5. Credentials: release 1 keeps each portal's existing scoped key behind the
   one client. Release 2 adds one fleet login that yields short-lived,
   per-portal-audience tokens with revocation; each portal checks the token
   as scope ∩ project grant (the P3 contract), with no bypass for service
   principals on project-scoped routes.

## Affected users and systems

- Owner and agents (Claude Code, Codex, agy) on p620 and other dev hosts.
- Factory repo: new package under `shared/` (CLI + MCP), contract schema
  `apis/task-contract.schema.json` (`source_artifacts`, approval record).
- PFactory: keep approved steps from a submitted plan; accept the new
  contract fields. AIFactory: accept and record them. TFactory: test-by-repo
  entry used by `factory test`.
- AIFactory (registry and identity owner): token issuing and revocation for
  the fleet login (release 2); all four portals: accept that token.
- Existing per-portal MCP servers and `parr-run` skill keep working.

## Constraints

- No lockout: the legacy shared token, scoped `acw_` keys, local mode and
  existing MCP entries keep working throughout (P3 no-lockout rule).
- Unknown and invisible projects answer identically (404, D6) through the
  CLI too; the CLI must not add an existence oracle.
- Tokens never printed, logged or written into generated MCP configs; configs
  reference token files or a credential helper.
- The CLI is a thin client over existing REST routes; no new orchestrator
  (reuse CFactory run/pipeline status where it already answers "where is my
  work").
- A failed or rejected submit fails loudly with the portal's reason; it never
  falls back to a re-planned build (W0 rule).
- Release 2's fleet login must not widen any key's reach: effective access =
  min(token scope, project grant) at every portal.

## Open questions

1. Language for the CLI: Python (matches the `shared/factory-*` packages and
   the portals' MCP servers) or Go (single static binary for other hosts)?
   Default if unanswered: Python, packaged with the Nix flake.
2. Should release 1 ship before the fleet login, or both in one PR series?
   Default: release 1 first (CLI + MCP + contract fields), fleet login as a
   second plan under the same issue.
3. Where does `factory` get installed on hosts: Nix flake output consumed by
   `~/.config/nixos`, or `uv tool install` from the repo? Default: flake
   output; the nixos config change is a separate, owner-approved step.
