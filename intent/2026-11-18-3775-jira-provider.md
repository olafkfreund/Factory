# Intent: RFC-0022 Phase 3 - JiraProvider (REST v3)

## Problem

Phases 1 and 2 of RFC-0022 are merged: a work-item identifier is a string and
`WorkItemProvider` is separate from `CodeProvider`. Nothing implements the
work-item seam for Jira, so a tenant whose planning lives in Jira cannot use the
board. The tenant credential store (RFC-0020 Phase 3) holds one opaque string per
connection, and Jira Cloud needs an email plus an API token.

## Proposed outcome

- A `JiraProvider` in the hub `factory-github` providers package implements
  `WorkItemProvider` only (Jira REST v3, no code members).
- Jira status maps to the canonical `open`/`closed` state by status category
  (Done = closed, everything else, including unseen custom statuses, = open).
- Keys such as `PROJ-123` stay strings.
- The factory closes a Jira issue by an explicit transition to a Done-category
  status; it fails loudly when none is available. A PR cannot close it with `Closes #n`.
- CFactory can store a structured Jira credential (email, API token) encrypted like
  every other credential, never logged, never returned by a read API.
- A `jira` connection is rejected in CFactory unless a feature flag is on. Default off.

## Affected users and systems

Hub `shared/factory-github/providers/`; the four vendored copies (re-vendor after
merge); CFactory connection and credential layer. Existing GitHub/GitLab/ADO tenants
see no change.

## Constraints

- No real Jira is contacted. Tests use `httpx.MockTransport`.
- Feature off by default; owner supplies the Jira Cloud site, email and token later.
- Never print or log a credential.
- Do not edit the CFactory connection model beyond what the flag and credential need
  (team rfc22-mixed-tenant owns it).

## Open questions

Decisions taken from RFC-0022 (owner delegation 2026-11-18): status category
mapping (option 1); string identifier; structured credential; labels degrade
instead of crash on a locked-down project. None remain for the approver.
